# mini-v8 记忆管理系统

## 概述

mini-v8 的记忆管理系统负责管理 AI 助手的"记忆"——从短期对话历史到长期跨会话上下文。系统采用**分层存储 + 多级压缩**的策略，在保证 AI 不"失忆"的前提下，尽可能降低令牌消耗。

记忆系统分为七个层次：

```
会话记忆（Session Memory）    ← 结构化笔记，持久化到磁盘
    ↑ ↓
上下文构建（Context）          ← 系统提示 + 用户上下文
    ↑ ↓
对话历史（History）            ← 完整的消息列表
    ↓
多级压缩（Compaction）        ← 逐层缩减令牌
    ↓
API 投影（Projection）        ← 清理后的 API 请求
    ↓
会话存储（Session Store）     ← 磁盘持久化
```

## 一、短期记忆：对话历史

### 是什么

短期记忆就是当前对话中所有的消息列表。每条消息包含角色（user/assistant/system）和内容（文本或内容块数组）。这是 AI 理解当前上下文的基础。

### 生命周期

1. **创建**：用户开始新对话时，创建一个空消息列表
2. **增长**：每一轮对话（用户提问 + AI 回答）追加到列表末尾
3. **压缩**：当列表太长时，触发压缩机制缩减
4. **边界标记**：压缩后的消息被边界标记（CompactBoundary）记录，后续 API 请求只发送边界之后的消息

### 管理算法

短期记忆本身不做特殊处理——它是所有其他系统操作的原材料。系统通过以下方式间接管理它：

- **API 投影**：在每次发送给 AI 之前，从完整消息列表中裁剪出活跃部分（最后一个边界之后的消息）
- **压缩触发**：当活跃消息的估算令牌数超过上下文窗口减去缓冲区大小时，触发压缩
- **缓冲区大小**根据模型上下文窗口自动调整：
  - 800K 以上模型：保留 50K 令牌缓冲区
  - 400K 以上模型：保留 30K 令牌缓冲区
  - 200K 以上模型：保留 20K 令牌缓冲区
  - 更小模型：保留窗口的 30%

## 二、会话记忆：结构化笔记

### 是什么

会话记忆（Session Memory）是系统在对话过程中自动提取的结构化笔记。它不是原始对话文本，而是经过提炼的关键信息，保存在一个 Markdown 文件中，持久化到磁盘。

### 笔记分类

系统使用正则表达式从对话中提取三类笔记：

1. **用户请求**（user-request）：从用户消息中提取，通常是用户提出的需求或问题
2. **决策记录**（decision）：从 AI 助手的回复中提取包含决策关键词的句子（"我来"、"让我们"、"我们应该"、"计划是"等）
3. **文件路径**（context）：从消息中提取的代码文件路径引用

### 提取算法

提取过程在"采样后钩子"中执行，不会阻塞主对话流程：

1. **触发检查**：每次 AI 回复后，检查是否需要执行提取
   - 首次提取：需要至少积累 2,000 令牌
   - 后续提取：自上次提取以来至少增长 1,000 令牌
2. **提取执行**：将当前消息列表传递给提取函数，运行正则匹配
3. **去重与追加**：新提取的笔记与已有笔记合并，按分类组织
4. **持久化**：将更新后的笔记写入磁盘上的 Markdown 文件

### 持久化格式

笔记文件存储在 `~/.claude-code-mini/session-memory/{sessionId}.md`，采用 Markdown 格式：

- 头部元数据：Session ID、最后总结消息 ID（LastSummarizedMessageId）
- 分类标题：## User Requests、## Decisions Made、## Context & Files
- 列表内容：按时间顺序排列的笔记条目

### 读取与恢复

- **读取**：`readSessionMemory()` 解析 Markdown 文件，返回笔记列表，同时恢复元数据（如 lastSummarizedMessageId）
- **注入到提示**：`getSessionMemoryForPrompt()` 将笔记格式化为提示文本，支持限制每类笔记数量和总字符数
- **空内容检测**：`isSessionMemoryEmpty()` 检查文件是否只有模板没有实际内容

### 阈值与限制

- 每类笔记数上限：3 条（普通注入）/ 5 条（压缩注入）
- 总字符上限：900 字符（普通注入）/ 2000 字符（压缩注入）
- 总会话记忆上限：30 条笔记

## 三、上下文构建：系统 + 用户上下文

### 是什么

上下文构建系统在每次 API 调用前组装两段信息：系统上下文（项目相关信息）和用户上下文（当前环境信息）。这些信息被注入到系统提示中，帮助 AI 理解当前工作环境。

### 系统上下文

系统上下文包含以下信息：

1. **Git 状态**：运行 `git status --short`、`git log -5`、`git branch`、`git config user.name`，输出截断到 1,000 字符
2. **项目指令**：从 CLAUDE.md 文件中读取的项目级指令
3. **记忆文件**：用户自定义的记忆文件内容

系统上下文在会话期间只计算一次（使用缓存），除非压缩后主动清除缓存。

### 用户上下文

用户上下文包含：

1. **CLAUDE.md 文件**：发现并读取项目层级的所有 CLAUDE.md 文件（可通过 `--bare` 禁用）
2. **当前日期**：以 ISO 格式注入当前日期

用户上下文同样在会话期间缓存，压缩后清除缓存以重新发现更新后的文件。

### 缓存策略

- 系统上下文和用户上下文使用 memoize（记忆化）缓存
- 缓存在以下情况被清除：
  - 会话记忆提取完成
  - 压缩后
  - 主动调用 `invalidateSystemContextCache()`
- 子代理执行压缩时不会清除主线程的缓存（避免状态损坏）

## 四、多级压缩系统

压缩系统是记忆管理的核心。它采用"从轻到重"的逐层递进策略：先尝试最轻量的方法，如果还不够，再逐步加大力度。

### 第一层：微压缩（Micro-compaction）

**目的**：在不改变对话结构的前提下，清除旧工具的输出内容。

**触发条件**：工具结果数量超过阈值（默认 6 个）。

**算法**：
1. 扫描所有用户消息中的 tool_result 块
2. 识别"可压缩"的工具（Bash、Read、Write、Edit、Grep、Glob、WebFetch、WebSearch）
3. 保留最近 N 个结果（默认 3 个），将更旧的结果内容替换为"[Earlier tool result compacted to reduce token usage.]"
4. 同时支持按位置阈值压缩：超过指定位置的消息中的工具结果也被清除

**特点**：
- 最轻量、最安全，不改变对话结构
- 只清理"工具结果"，不动用户说的话和 AI 的回答
- 缓存微压缩状态，如果消息没变就不重复计算

### 第二层：工具结果预算（Tool Result Budget）

**目的**：对每个工具结果设定令牌上限，超过的部分用预览摘要代替。

**触发条件**：始终运行（在每次 API 投影时都会尝试）。

**算法**：
1. 收集所有"可压缩"工具的结果，提取前 320 字符作为预览
2. 按消息分组，每组独立计算预算
3. 首先压缩单条结果过大的（超过 800 令牌/条）
4. 如果消息级总令牌数仍超过上限（1,200 令牌/条），继续压缩剩余的大结果
5. 压缩过的结果会被记录，下次不再重复压缩（除非内容变化）

**替换格式**：
```
[Compacted {工具名} result: showing first {字符数} chars of {总字符数}]
{预览内容}
[Large tool result compacted to reduce token usage.]
```

**特点**：
- 跨投影持久化替换状态（ToolResultBudgetState）
- 新出现的结果优先压缩
- 不会压缩已标记为错误的结果

### 第三层：语义压缩（Semantic Compaction）

**目的**：把最旧的一段对话整体替换为结构化摘要。

**触发条件**：微压缩和工具预算处理后，令牌数仍超过阈值。

**算法**：
1. **保留最近的 N 对消息**（默认 3 对，即 3 问 3 答）
2. **调整边界**：确保 tool_use/tool_result 配对不被切断
3. **生成摘要**：
   - 如果会话记忆可用：使用会话记忆笔记作为摘要（无需额外 LLM 调用）
   - 否则：使用启发式算法从旧消息中提取关键信息
4. **构建结果**：系统消息 + 摘要消息 + 保留的最近消息

**启发式摘要内容**：
- 被移除的消息数量
- 使用的工具列表
- 最近的用户请求内容（最后 4 条，每条前 200 字符）
- AI 的决策句子（最后 3 条回复中的关键词句子）

### 第四层：会话记忆压缩（Session Memory Compaction）

**目的**：使用持久化的会话记忆笔记完全替代传统的语义压缩，无需 LLM 调用，无需启发式摘要。

**触发条件**：由配置开关 `sessionMemoryCompactEnabled` 控制（默认开启），在语义压缩之前优先尝试。

**算法**（`trySessionMemoryCompaction`）：

1. **门控检查**：
   - 配置是否启用
   - 会话 ID 是否存在
   - 会话记忆文件是否存在且非空
   - 记忆内容是否包含有效笔记（非空模板）

2. **计算保留边界**（`calculateMessagesToKeepIndex`）：
   - 从 `lastSummarizedMessageId`（上次总结的消息指纹）之后开始
   - 向后扩展，直到满足最低要求：
     - 至少保留 10,000 令牌的消息
     - 至少保留 5 条包含文本块的消息
   - 在 40,000 令牌处停止（硬上限）
   - 地板为索引 1（索引 0 是系统消息）

3. **API 不变性保护**（`adjustIndexToPreserveAPIInvariants`）：
   - 扫描保留范围内的 tool_result 块
   - 如果某个 tool_result 的 tool_use 不在保留范围内，向后扩展索引以包含该 tool_use
   - 确保 API 契约不被违反

4. **构建压缩结果**：
   - 截断会话记忆内容（每段限制，总限制）
   - 注入 `SESSION_MEMORY_COMPACTION_MARKER` + 截断后的记忆 + 令牌节省统计
   - 返回紧凑的消息数组：系统消息 + 摘要消息 + 保留消息

**输出格式**：
```
[Earlier conversation summarized from session memory]
## Session Memory (auto-extracted)
{截断后的会话记忆内容}

[Compacted {数量} messages using session memory, saving approximately {令牌数} tokens]
```

**特点**：
- 完全替代 LLM 压缩，节省 API 成本
- 保留更丰富的上下文（结构化笔记，非简化摘要）
- 支持通过 `sessionMemoryCompactEnabled` 配置关闭
- 阈值可配置：minTokens（10K）、minTextBlockMessages（5）、maxTokens（40K）

### 第五层：Snip 裁剪（Snip Compaction）

**目的**：在对话中插入一个"剪刀标记"，标记之前的所有消息在后续 API 请求中直接被过滤掉。

**触发条件**：对话超过 30 条消息时，系统在提示中嵌入"考虑使用 Snip"的建议。用户可通过 `/force-snip` 命令手动触发。

**算法**（`snipCompactIfNeeded`）：
1. 从消息列表末尾向前扫描，查找 `snip_boundary` 类型的系统消息
2. 提取 `snipMetadata.removedUuids` 数组（被移除消息的 UUID 列表）
3. 从消息列表中过滤掉所有 UUID 在移除列表中的消息
4. 返回过滤后的消息数组和释放的令牌数估计

**投影算法**（`projectSnippedView`）：
- 遍历所有消息，收集所有 snipping 边界的 removedUuids
- 创建一个全局的被移除 UUID 集合
- 过滤掉所有匹配的消息
- 在 API 投影步骤中使用，确保被裁剪的消息不会发送给 AI

**特点**：
- 比语义压缩更激进——不是摘要，是直接移除
- Snip 边界作为系统消息持久化在对话中
- 跨会话边界累积（每个边界添加新的 removedUuids）

### 应急防线：反应式压缩（Reactive Compaction）

**目的**：AI 服务器返回"请求太长"错误时自动启动的应急处理。

**触发条件**：API 返回 `prompt_too_long`、`too large`、`too long`、`maximum context length`、`context window`、`413` 等错误。

**算法**（逐级尝试，直到成功）：

```
第 0 步：尝试会话记忆压缩
第 1 步：微压缩工具结果 → 如果满足预算则返回
第 2 步：语义压缩（保留 2 对消息）→ 如果满足预算则返回
第 3 步：语义压缩（只保留 1 对消息）→ 如果满足预算则返回
第 4 步：按 API 轮次分组，丢弃最旧的一组 → 如果满足预算则返回
第 5 步：返回失败
```

**特点**：
- 被动触发，正常情况不会走这个流程
- 逐级加大力度，尽可能在最小损失下解决问题
- 每次成功压缩后执行后压缩清理

### 压缩边界管理

每次语义压缩或会话记忆压缩后，系统记录一个"压缩边界"（CompactBoundary），包含：

- 边界 ID 和时间戳
- 压缩前消息数 / 压缩后消息数
- 是否使用了会话记忆
- 摘要预览（前 240 字符）
- 最后总结消息 ID（用于后续压缩边界追踪）

**边界的作用**：
- 后续 API 投影只发送最后一个边界之后的消息
- 会话恢复时，从最后一个边界的 lastSummarizedMessageId 恢复边界追踪
- 边界在对话序列化/反序列化时被持久化和恢复

## 五、API 投影：消息准备管道

### 是什么

API 投影是消息发送给 AI 之前的最后处理步骤。它从完整的对话缓冲区中生成一个经过清理、压缩、预算的"投影"，既保证了数据的完整性（原始消息不变），又控制了令牌消耗。

### 处理管道（`projectMessagesForAPI`）

```
完整消息列表
    ↓
① 边界切割：只取最后一个 CompactBoundary 之后的消息
    ↓
② Snip 过滤：移除被 Snip 标记裁掉的消息
    ↓
③ 工具结果恢复：从磁盘恢复被持久化的工具结果内容
    ↓
④ 微压缩：清除旧工具结果
    ↓
⑤ 工具结果预算：用预览替换大结果
    ↓
⑥ 检查是否需要语义压缩
    ├─ 需要 → ②尝试会话记忆压缩 (trySessionMemoryCompaction)
    │          └─ 成功 → 使用 SM 压缩结果
    │          └─ 失败 → 回退到传统语义压缩 (compactMessages)
    └─ 不需要 → 直接发送
    ↓
⑦ 估算最终令牌数
    ↓
⑧ 返回投影结果（含头寸信息：预估令牌数、头寸比例等）
```

### 对话缓冲区（ConversationBuffers）

对话缓冲区是一个数据结构，保存了完整的对话状态：

- **fullMessages**：完整的消息历史列表
- **messageUuids**：每条消息对应的 UUID
- **forceCompactNextProjection**：强制下次投影时压缩的标志
- **toolResultBudgetState**：工具结果预算状态（已替换的结果记录）
- **compactBoundaries**：压缩边界历史记录

### 提交压缩到缓冲区（可选）

当 `commitCompactionToConversation` 为 true 时，压缩结果会写回到对话缓冲区：

1. 保留压缩边界之前的前缀消息
2. 创建新的 CompactBoundary 元数据（含 lastSummarizedMessageId）
3. 将压缩后的消息写入 fullMessages
4. 重建工具结果预算状态
5. 清除强制压缩标志
6. 使系统上下文缓存失效

## 六、会话存储：磁盘持久化

### 是什么

会话存储系统将会话的完整状态以 JSON 格式持久化到磁盘，支持会话的恢复和"最新的会话"发现。

### 存储位置

会话文件存储在 `~/.claude-code-mini/sessions/{sessionId}.json`

### 快照结构

保存的快照包含：

- **元数据**：版本号、保存时间、会话 ID、当前工作目录、模型名称
- **会话数据**：
  - fullMessages：完整消息列表
  - messageUuids：消息 UUID 列表
  - forceCompactNextProjection：强制压缩标志
  - toolResultBudgetRecords：工具结果预算记录
  - compactBoundaries：压缩边界历史

### 恢复流程

```
按会话 ID 加载 → 读取 JSON 文件 → 验证版本
  → createConversationBuffers(快照数据)
    → 重建消息列表
    → 重建工具结果预算状态（reconstructToolResultBudgetState）
    → 恢复压缩边界
  → restoreLastSummarizedMessageIdFromBoundaries（恢复边界追踪）
```

### 最新会话恢复

`loadLatestConversationSnapshot()` 按修改时间扫描会话目录，加载最新的有效快照，用于断线重连场景。

## 七、长期记忆：跨会话上下文

### 是什么

长期记忆系统通过以下机制实现跨会话的上下文延续：

1. **CLAUDE.md 文件**：项目根目录下的指令文件，在每次会话中自动读取并注入
2. **会话记忆文件**：每个会话的笔记文件独立存储，但可以通过会话 ID 恢复
3. **会话存储**：完整的对话状态持久化，支持"回到之前会话继续"

### 跨会话数据流

```
会话 A → 会话记忆提取 → 持久化到 disk
  → 压缩边界记录 lastSummarizedMessageId
  → 会话存储快照（含所有边界和状态）
  
会话 B（resume）→ 加载会话存储快照
  → 恢复对话缓冲区
  → 恢复压缩边界（restoreLastSummarizedMessageIdFromBoundaries）
  → 恢复会话记忆（readSessionMemory）
  → 继续对话，AI 知道之前发生了什么
```

### 记忆文件系统

- 会话记忆文件：`~/.claude-code-mini/session-memory/{sessionId}.md`
- 会话存储文件：`~/.claude-code-mini/sessions/{sessionId}.json`
- 存储目录可通过 `setSessionMemoryDir()` 和 `setSessionStoreDir()` 覆盖（用于测试隔离）

## 八、完整数据流：一次对话请求的生命周期

### 正常路径

```
用户输入消息
  ↓
追加到对话缓冲区（pushMessageWithUuid）
  ↓
检查是否需要提取会话记忆
  ├─ 需要 → 异步提取笔记 → 持久化
  └─ 不需要 → 继续
  ↓
API 投影（projectMessagesForAPI）
  ↓
发送给 AI
  ↓
处理 AI 回复
  ↓
更新会话记忆（如果有新内容）
  ↓
会话存储快照
  ↓
等待下一轮
```

### 压缩路径

```
API 投影阶段：
  needsCompaction() 返回 true
  ↓
trySessionMemoryCompaction() — 尝试 SM 压缩
  ├─ 成功 → 使用 SM 结果
  └─ 失败 → compactMessages() — 传统语义压缩
  ↓
commitCompactedProjectionToConversation() — 提交到缓冲区
  ↓
runPostCompactCleanup() — 清理缓存
  ↓
继续发送给 AI
```

### 错误恢复路径

```
API 返回 prompt_too_long 错误
  ↓
reactiveCompact() — 反应式压缩
  ├─ 0: 尝试 SM 压缩
  ├─ 1: 微压缩
  ├─ 2: 语义压缩（保留 2 对）
  ├─ 3: 语义压缩（保留 1 对）
  └─ 4: 丢弃最旧 API 轮次组
  ↓
runPostCompactCleanup()
  ↓
重试 API 请求
```

### 会话恢复路径

```
加载最新会话快照
  ↓
createConversationFromSnapshot()
  ├─ createConversationBuffers(快照数据)
  └─ restoreLastSummarizedMessageIdFromBoundaries()
  ↓
initSession(会话 ID) — 恢复会话记忆
  ↓
继续对话，AI 可以访问之前的上下文
```

## 十、设计原则

### 1. 从轻到重

先用成本最低、信息损失最小的方法，逐步加大力度。微压缩（零成本）→ 工具预算（零成本）→ SM 压缩（零成本）→ 语义压缩（需一次 API 调用）→ Snip 裁剪（永久删除）。

### 2. 近详远略

最近的对话保留最完整，越旧的越可能被压缩或裁剪。所有压缩算法的核心都是"从尾部开始保留，从头部开始裁剪"。

### 3. 可追溯

每次压缩都留下边界记录（CompactBoundary），知道"什么时候压缩了什么"。边界包含 lastSummarizedMessageId，支持跨压缩周期的边界追踪。

### 4. 无感知

用户不需要手动管理记忆——提取、压缩、存储都是自动的。只有当对话极长（30+条）时，系统才会提示用户考虑使用 `/force-snip`。

### 5. 成本可控

每层都在限制令牌消耗，避免压缩本身产生过高成本。SM 压缩完全避免了 LLM API 调用，是最经济的压缩方式。

### 6. 应急兜底

API 拒绝时自动降级（反应式压缩），不会让用户遇到无法继续的情况。从最轻量的方法开始，逐级增加力度，确保总有办法继续对话。

### 7. 持久化保障

所有关键状态都会持久化到磁盘：会话笔记、压缩边界、工具结果预算、消息 UUID。即使终端关闭，恢复后也能继续之前的对话。

### 8. 不可变性

原始消息永不修改——API 投影从完整消息列表中生成处理后的快照。工具结果替换使用新的对象而不是修改原始消息。这保证了数据的一致性和可追溯性。
