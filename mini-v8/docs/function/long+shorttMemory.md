# 对话记忆压缩系统

## 一句话说明

AI 助手和用户的对话会越来越长，每次对话都把所有历史发给 AI，既费钱又容易超出字数限制。这个系统的作用就是——**在不让 AI 失忆的前提下，把对话历史变短**，就像把一整天的会议记录浓缩成一张 A4 纸的会议纪要。

---

## 一、为什么要压缩？

AI 模型每次处理对话，都有"注意力窗口"限制（比如一次只能看 20 万字）。对话长了以后：

| 问题 | 后果 |
|------|------|
| 超出窗口限制 | 请求直接被拒绝，无法继续工作 |
| 接近窗口上限 | Token 消耗大，API 费用高，响应变慢 |
| 历史细节太多 | 最近的指令反而不容易被 AI 关注到 |

压缩的本质是：**用高质量摘要替代原始细节，在不丢失关键信息的前提下减少字数。**

---

## 二、整体架构：四层过滤 + 三个防线

系统采用"逐层递进"的策略：先尝试最轻量的方法，如果还不够，再逐步加大力度。

```
第一层：即时轻量清理  →  第二层：按预算裁剪  →  第三层：语义摘要  →  第四层：暴力截断
                              ↓
                    API 返回"超长"错误时触发应急措施
```

---

## 三、各层机制详解

### 第一层：微压缩（Micro-compaction）

**做什么：** 把老旧对话中那些"大段工具执行结果"清空，替换成一句"此处省去 XX 结果"。

**典型场景：** 用户让 AI 连续读取了 10 个文件，每个文件内容几千字。AI 读取完之后，这些文件内容对后续对话已经没有用了，但还占着大量空间。

**特点：**
- 最轻量、最安全，不改变对话结构
- 只清理"工具结果"（如 Bash 命令输出、文件读取内容），不动用户说的话和 AI 的回答
- 保留最新的几个结果（默认 3 个），方便当前操作参考
- 每轮都会缓存，如果消息没变就不重复计算

**打个比方：** 会议室白板上写满了上个月的讨论笔记——不清除白板，只是把最旧的那几行擦掉，留出空间写今天的内容。

---

### 第二层：工具结果预算（Tool Result Budget）

**做什么：** 对每一个工具结果设定"字数上限"，超过的部分用预览摘要代替。

**典型场景：** `grep` 命令返回了 5000 行匹配结果，但用户实际只看了前几行。

**特点：**
- 按"每条消息"和"每个结果"分别设限（消息级 1200 字，结果级 800 字）
- 用类似 `[Compacted Bash 结果：显示前 320 字，共 20000 字]` 的形式替代
- 系统会"记住"哪些结果已经被压缩过，避免重复处理
- 新出现的结果优先压缩（因为旧结果已经在上一轮被处理过了）

**打个比方：** 不是把整本小说都放进背包，只撕下目录和前三页——告诉你这本书讲了什么，但不用背整本。

---

### 第三层：语义压缩（Semantic Compaction）

**做什么：** 把最旧的一段对话（多轮用户问 + AI 答）整体拿掉，替换成一段"会议纪要"。

**典型场景：** 用户和 AI 已经聊了 50 轮，讨论了架构设计、改了很多代码、修了几个 Bug。前 40 轮的内容仍然完整保留在对话里，但最近 10 轮才是当前关注的焦点。

**特点：**
- 保留系统预设指令 + 最近几轮对话（默认保留最近 3 轮，即 3 问 3 答）
- 被移除的旧对话自动生成一段结构化摘要：
  - 用户问了什么
  - 用了哪些工具
  - AI 做了什么决定
  - 出了什么错、怎么修的
- 有两种模式：
  - **本地摘要（免费）**：由代码内部的规则自动生成，速度快但不精确
  - **AI 摘要（需一次额外 LLM 调用）**：把旧对话发给 AI，让它写一份 9 段结构的正式纪要，质量更高

**打个比方：** 团队开了 3 小时会，前 2 小时的讨论被整理成 2 段会议纪要贴在墙上，后 1 小时的内容保持原样。新来的人看纪要 + 最近内容就能跟上。

#### 摘要的 9 段结构（AI 模式）

AI 生成的摘要包含以下板块：

1. **核心诉求** — 用户到底想干什么
2. **关键技术点** — 涉及什么技术、框架
3. **文件与代码** — 读了/改了哪些文件，代码片段
4. **错误与修复** — 出了什么错，怎么修的
5. **已解决问题 & 正在调试的问题** 
6. **用户所有原始消息** — 确保不遗漏用户反馈
7. **待办事项** — 明确说好但还没做的事
8. **当前工作状态** — 压缩前那一刻正在做什么
9. **下一步建议** — 基于上下文推荐继续的方向

---

### 第四层：Snip 裁剪（Snip Compaction）

**做什么：** 在对话流中插入一个"到此为止"标记，标记之前的所有消息在下次发送给 AI 时直接被过滤掉，永不再用。

**典型场景：** 一次非常长的会话（50+ 轮）后，前面的内容已经经过了多次摘要，摘要本身也越来越长，需要彻底清理。

**特点：**
- 比语义压缩更激进——不是摘要，是直接移除
- 在对话中插入一个"剪刀标记"，标记前端内容为"已裁剪"
- 下次准备发送给 AI 时，裁剪模块自动过滤掉被标记的消息
- 裁剪边界会被记录，后续操作可以追踪"什么时候裁了多少条"
- 当对话超过 30 条消息时，系统会提示用户考虑使用 Snip

**打个比方：** 整理文件夹——不是把所有旧文件压缩打包，而是直接扔进碎纸机，只在文件夹里留一个标签"这里原有多少个文件已于某日清理"。

---

### 应急防线：反应式压缩（Reactive Compaction）

**做什么：** AI 服务器返回"你的请求太长了"错误时，自动启动应急压缩。

**触发条件：** API 返回 `prompt_too_long`、`too large`、`413` 等错误。

**处理步骤（按顺序尝试，直到成功）：**
1. 微压缩工具结果
2. 语义压缩（保留 2 轮对话）
3. 语义压缩（只保留 1 轮对话）
4. 按 API 轮次分组，直接丢弃最旧的一组

**特点：**
- 被动触发，正常情况不会走这个流程
- 逐级加大力度，尽可能在最小损失下解决问题
- 如果所有方法都失败，只能返回失败（但极少发生）

---

### 辅助机制

#### 会话记忆（Session Memory）

- 系统会跨会话持久化一些关键信息（用户偏好、项目上下文等）
- 在压缩时，这些持久记忆会被注入到摘要中，确保压缩后仍能保留重要上下文
- 压缩后的摘要会打上特殊标记，避免重复注入同一份记忆

#### API 端微压缩（Server-side Micro-compaction）

- 部分场景下可以直接告诉 AI 服务器"帮我自动清理旧工具结果"
- 服务器会在处理请求之前自行清理，客户端不需要做额外工作
- 通过环境变量控制开关和阈值

#### 缓存清理（Post-compaction Cleanup）

- 每次压缩后，自动重置各种内部缓存
- 确保下一轮对话不会使用过时的缓存数据
- 触发系统提示重新组装

#### 按轮次分组丢弃（Group-based Dropping）

- 将对话按"用户提问 + AI 回答"分成一个个轮次组
- 在极端情况下（所有压缩手段都无效），直接丢弃最旧的一组
- 这是最后手段，相当于"断尾求生"

---

## 四、完整流程：一次对话请求的生命周期

当一个请求准备发送给 AI 时，系统按以下顺序处理：

```
① Snip 过滤
   ↓
② 从磁盘恢复大型工具结果（如果有）
   ↓
③ 缓存微压缩（如果消息没变，跳过）
   ↓
④ 工具结果预算裁剪（缩减大结果）
   ↓
⑤ 检查是否需要语义压缩
   ├─ 不需要 → 直接发送
   └─ 需要   → 执行语义压缩，注入摘要
       ↓
⑥ 估算最终 Token 数
   ↓
⑦ 发送给 AI
   ↓
⑧ 如果 AI 返回"太长"错误 → 启动反应式压缩 → 重试
```

---

## 五、设计原则

| 原则 | 说明 |
|------|------|
| **从轻到重** | 先用成本最低、信息损失最小的方法，逐步加大力度 |
| **近详远略** | 最近的对话保留最完整，越旧的越可能被压缩或裁剪 |
| **可追溯** | 每次压缩都留下边界记录，知道"什么时候压缩了什么" |
| **无感知** | 用户不需要手动管理，系统自动判断和执行 |
| **成本可控** | 每层都在限制 Token 消耗，避免压缩本身产生过高成本 |
| **应急兜底** | API 拒绝时自动降级，不会让用户遇到无法继续的情况 |

---

## 六、总结

这个系统本质上是一个**多级过滤器**：

- **日常运行中**：微压缩 + 工具预算自动工作，用户无感知地节省 30%-70% 的 Token
- **对话变长时**：语义压缩介入，用摘要替代旧对话，保证 AI 不"失忆"
- **对话极长或出错时**：Snip 裁剪 + 反应式压缩兜底，确保服务不中断

最终效果是：**用户和 AI 可以聊得更久、更深入，而不会因为对话太长而中断或花费过高的费用。**
