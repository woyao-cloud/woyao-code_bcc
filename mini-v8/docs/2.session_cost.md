  差异判断

  src 更成熟的地方主要有 4 类：

  1. system context 的缓存和失效机制更完整
     src/context.ts:116 是 conversation 级 memoize，不只是局部缓存 CLAUDE.md / skills。
     另外 systemPromptSections 明确支持 section cache 与 /clear、/compact 失效，src/constants/
     systemPromptSections.ts:17。
  2. tool result 的预算控制细很多
     src 不是粗粒度“老 tool result 统一 stub”，而是按 message 分组、按 tool_use_id 冻结决策、持久化 preview、resume 后重
     建 replacement state，核心在 src/utils/toolResultStorage.ts:739 和 src/utils/toolResultStorage.ts:939。
     这比 mini-v8 当前的 microcompact 更稳，也更省 token。
  3. compact boundary / resume 语义更完整
     src 会把 compact boundary 当成一等消息处理，并在 compact 后释放 pre-boundary history，同时兼顾 transcript/resume，
     src/QueryEngine.ts:700 src/QueryEngine.ts:957。
     mini-v8 现在更偏“projection 优先”，对长期 resume/debug 语义还没完全补齐。
  4. session memory / autocompact 整体链路更老练
     src 这块有更多防抖、阈值、fork/cache-safe 处理，src/services/compact/autoCompact.ts:316 和 src/services/
     SessionMemory/sessionMemory.ts:323。
     不过 mini-v8 已经拿到了最核心的 token-saving 思路，差距主要在工程稳健性，不在方向。

  给 mini-v8 的下一阶段优化路线

  P6 我建议先做 system context 全量 memoization + 明确失效。

  - 现在 mini-v8 只缓存了 CLAUDE.md 和 skills 片段，mini-v8/src/context.ts:111
  - 还缺 conversation 级 getSystemContext() 缓存
  - 同时要在 /clear、/compact、cwd 变化、memory/agent/teams 变化时失效
  - 这是低风险、稳定省 token 和省 latency 的项

  P7 做 query-aware teams + team memory 真正接线。

  - 现在 teams 还是 getTeamsForPrompt() 直接拿，mini-v8/src/context.ts:302
  - includeTeamMemory 目前基本是空位，mini-v8/src/context.ts:320
  - 这块补齐后，agent/team 类 prompt 注入会更收敛，不会长期把无关团队信息带进系统提示

  P8 做更细粒度的 tool result budgeting。

  - 目标不是替换现有 microcompact，而是在 messagesForAPI 投影阶段叠加一层“按 message / per-result budget”的预算器
  - 学 src/utils/toolResultStorage.ts 的三点：
      - replacement 决策按 tool_use_id 冻结
      - preview/stub 可复用，避免每轮重复变化影响 cache
      - resume 后可重建 replacement state
  - 这是继续降 token 的最高价值项之一，尤其是工具输出大的场景

  P9 做 compact boundary 元数据和 resume-aware projection。

  - 现在 mini-v8 的 fullMessages / messagesForAPI 已经把“展示”和“发 API”分开了，这是对的
  - 下一步是给 compact 结果打边界，让历史折叠后的语义可恢复、可调试、可 resume
  - 这一步对“省 token”是间接收益，但会让后续裁剪、stub、summary 全都更稳

  P10 再考虑把 session memory 和 context selector 做更统一的预算仲裁。

  - 当前 session memory 已经能参与 compact，也能按策略注入 prompt
  - 但它和普通 memories / agents / teams 还属于分段决策
  - 后面可以把它们统一进一个“context block scorer + budget allocator”，用 relevance + recency + size 统一裁决
  - 这一步收益更偏长期架构，不是最先做的

  如果只按“减少 token 消耗”排优先级

  1. P8 细粒度 tool result budgeting
  2. P6 getSystemContext() 全量缓存与失效
  3. P7 query-aware teams + team memory
  4. P9 compact boundary + resume-aware projection
  5. P10 统一 context budget scorer

  一句话判断

  如果和 src 对比，mini-v8 现在最大的缺口已经不是“有没有 compact / session memory / projection”，而是：

  - tool result 预算还不够细
  - system context 缓存与失效还不够完整
  - compact boundary / resume 语义还不够强

  如果你要继续，我建议直接开做 P6 + P8，这两项对 token 和稳定性最有价值。
