# 第四章：Memory 体系与个性配置

AI 编程助手的"记忆"是一个多层、多生命周期的体系。从跨会话持久化记忆到会话内的临时状态，从用户显式设置的指令到系统自动提取的偏好，Claude Code 的 Memory 体系贯穿整个产品体验。

## 4.1 记忆的分层架构

Claude Code 的记忆体系分为五个层次，每层有不同的持久化程度和生命周期：

```
┌──────────────────────────────────────────────────────┐
│  第一层：CLAUDE.md（永久，用户显式写入）              │
│  项目级指令文件，随仓库版本管理                      │
├──────────────────────────────────────────────────────┤
│  第二层：Settings（永久，用户配置）                   │
│  settings.json 中的系统提示词、权限模式、模型偏好     │
├──────────────────────────────────────────────────────┤
│  第三层：Memory 文件（永久，AI 自动提取）              │
│  extractMemories 在会话结束后提取的关键信息            │
├──────────────────────────────────────────────────────┤
│  第四层：会话内 Memory（会话级，AI 维护）              │
│  LLM 在 system prompt 中维护的"会话记忆"              │
├──────────────────────────────────────────────────────┤
│  第五层：Compaction 摘要（会话级，自动生成）           │
│  压缩后的对话摘要，保留已完成任务的关键信息           │
└──────────────────────────────────────────────────────┘
```

## 4.2 CLAUDE.md：项目级指令体系

CLAUDE.md 是 Claude Code 最独特的记忆机制——它不是藏在数据库里的数据，而是**项目源码中的一个文件**，随 git 版本管理。

**三级级联规则**

CLAUDE.md 的加载遵循"就近覆盖"的级联规则：

1. **全局级**：`~/.claude/CLAUDE.md` — 用户的个人偏好（如"永远用 TypeScript"）
2. **项目级**：`<project>/CLAUDE.md` — 团队约定（如"使用 pnpm"、"测试用 vitest"）
3. **目录级**：`<project>/<subdir>/CLAUDE.md` — 模块说明（如"此目录负责认证逻辑"）

每一级的内容都会被读取并追加到 System Prompt 中。如果同级有冲突，后加载的覆盖先加载的。

**CLAUDE.md 的内容指南**

一个典型的 CLAUDE.md 包含：
- **命令指南**：如何安装、构建、测试
- **编码规范**：命名约定、代码风格
- **架构说明**：项目结构和关键模块
- **重要约束**：禁止的事项、必须遵循的规则

从设计角度看，CLAUDE.md 的巧妙之处在于：它把"AI 记忆"和"项目文档"合二为一。开发者本来就要写 README 和文档，CLAUDE.md 只需要额外补充"AI 需要知道但文档没写"的内容，没有新增认知负担。

## 4.3 Memory 文件：AI 自动提取

`extractMemories` 模块是 Memory 体系的"大脑"——它在对话结束后自动分析对话内容，提取关键信息并持久化。

**触发时机**

当一次对话结束时（非用户显式中断），后台会启动 `extractMemories` 流程：

1. 将最近的对话消息发送给 LLM（通常是 Haiku，成本低）
2. LLM 分析消息，提取"值得记住"的信息
3. 提取的信息格式化后写入 Memory 文件

**提取的信息类型**

系统会提取以下类别的信息：
- **用户偏好**：喜欢用哪种语言、哪种框架、哪种测试工具
- **项目约定**：项目使用的命名规范、代码风格
- **技术决策**：为什么选择某个方案、放弃了哪些替代方案
- **工作流模式**：常用的操作流程（如"总是先 lint 再提交"）

**Memory 文件存储**

Memory 文件存储在 `~/.claude/memories/` 目录下，每个 Memory 是一个结构化的 markdown 文件：

```markdown
---
name: <唯一标识>
description: <一句话摘要>
metadata:
  type: user | feedback | project | reference
---

<记忆内容>
```

**不提取什么**

同样重要的是，系统知道**不**提取什么：
- 临时调试信息
- 一次性命令操作
- 敏感的凭证或密钥
- 用户明确表示不需要记住的内容

## 4.4 Hooks 系统

Hooks 是 Claude Code 的"生命周期回调"机制。它在 Agent 运行的关键节点注入用户自定义逻辑，是实现个性配置的核心管道。

**Hook 类型**

系统定义了多种 hook 类型：

```typescript
type HookType =
  | 'pre_compact'    // 压缩前：注入压缩时要保留的指令
  | 'post_compact'   // 压缩后：清理或通知
  | 'pre_query'      // 查询前：注入额外 System Prompt
  | 'post_query'     // 查询后：记录或清理
  | 'turn_start'     // 回合开始
  | 'turn_end'       // 回合结束
```

**Hook 的执行**

Hook 在 `src/utils/hooks.ts` 中管理。每个 Hook 是一个可执行块，接收当前上下文，返回影响或副作用：

```
Pre-Compact Hook:
  输入：当前消息列表、压缩参数
  输出：自定义指令（影响压缩方向）、用户展示消息（反馈给用户）

Post-Compact Hook:
  输入：压缩结果、新旧 token 数
  输出：无副作用（仅清理或记录）

Pre-Query Hook:
  输入：即将发送的 System Prompt 和 Messages
  输出：追加的 System Prompt 内容
```

**Hook 来源**

Hook 可以来自多个来源，优先级从高到低：
1. `policySettings` — 企业策略（强制，不可绕过）
2. `pluginHook` — 插件注册的钩子
3. `sessionHook` — 当前会话的钩子
4. `settings.json` — 用户配置的钩子
5. `builtinHook` — 系统内置的钩子

这种优先级设计让企业策略能够覆盖用户配置，插件能扩展系统能力，内置钩子提供基线功能。

**Hook 的应用场景**

- 企业可以在 pre_compact hook 中注入合规指令（"永远不要删除 compliance 目录的内容"）
- 团队可以在 pre_query hook 中注入代码审查规则
- 个人可以在 settings.json 中配置自定义 hook

## 4.5 用户偏好学习系统

除了显式配置和自动提取，系统还通过"行为观察"来学习用户偏好：

**权限模式学习**

当用户反复"允许"某个工具（如 Bash、Write），系统会学习这种模式：
- 首次使用时弹权限提示
- 用户选择"永远允许"
- 该工具被加入白名单，后续不再提示

这是通过 `settings.json` 中的 `permissions` 字段持久化的。

**Model 偏好**

用户通过 `/model` 命令切换模型后，选择会被记录。系统倾向于使用用户最近选定的模型。

**Effort 设置**

`/effort` 命令让用户控制 Agent 的"努力程度"（从简洁模式到深思熟虑模式）。选择也持久化到 settings。

**穷鬼模式（Budget Mode）**

通过 `/poor` 命令切换。启用后系统跳过 `extract_memories`、`prompt_suggestion` 和 `verification_agent` 等消耗 token 的后处理步骤。用户偏好持久化到 settings.json。

## 4.6 内存注入机制

在 System Prompt 组装阶段，Memory 的内容需要被注入。注入策略是：

**注入时机**

每次组装 System Prompt 时，都会检查 Memory 文件。具体来说：

1. 扫描 `~/.claude/memories/` 目录
2. 读取所有记忆文件
3. 筛选与当前项目相关的记忆
4. 格式化为"记忆段落"追加到 System Prompt

**范围控制**

不是所有记忆都注入——系统会筛选：
- **项目特定**：与当前项目关联的记忆优先
- **时间衰减**：太久远的记忆权重降低
- **相关性**：基于内容与当前任务的相关性

**格式**

注入到 System Prompt 的记忆保持简洁：

```
## 关于此用户的已知信息
- 偏好 TypeScript 而非 JavaScript
- 使用 pnpm 包管理器
- 项目使用 ESLint + Prettier 代码规范
```

## 4.7 记忆的维护与清理

记忆不是"写一次永远保留"的——系统有维护机制：

**自动清理**

- 时间衰减：旧记忆的优先级自动降低
- 重复合并：相似记忆会被合并
- 冲突检测：当新旧记忆矛盾时，保留较新的

**用户主动管理**

- `/forget` 命令：删除特定记忆
- `/remember` 命令：显式添加记忆
- Memory 文件可手动编辑

## 4.8 设计权衡讨论

**（1）自动提取 vs 用户控制**

自动提取记忆降低用户负担（不需要手动说"记住这个"），但可能提取用户不希望保留的信息。

方案：提取的信息限于"项目级别的、非敏感的、可公开的"内容。用户可以通过显式删除来控制。敏感信息（API key、密码）通过关键词过滤不会提取。

**（2）记忆的深度 vs 信息量**

记住太多细节会导致 System Prompt 臃肿；记住太少则帮助有限。

方案：只在 System Prompt 中注入"当前项目相关+最近"的记忆。完整的记忆库保持可查询状态，需要时才全量检索。

**（3）Hooks 的灵活性 vs 安全性**

Hooks 越灵活，能做更多事情（注入指令、修改行为），但安全隐患越大（恶意 hook 可以劫持系统）。

方案：Hook 有严格的来源分级和权限检查。企业 policy hook 是最高优先级，不可被用户 hook 覆盖。插件 hook 需要用户授权。

---

**本章小结**：Claude Code 的 Memory 体系是一个从 CLAUDE.md 到自动提取、从 Hooks 系统到偏好学习的完整架构。它将"AI 记忆"从技术问题提升为产品问题——不仅仅是"记住什么"，更是"如何记住、何时注入、怎样遗忘"。下一章将讨论 Agent 埋点与可观测性，让系统的每一次行为都有迹可循。
