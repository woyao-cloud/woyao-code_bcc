# 第五章：遥测与可观测性

## 问题背景

AI 编码工具的运行过程具有高度不确定性和非确定性——同样的用户请求可能因为模型版本、上下文窗口状态、工具执行顺序、甚至后端延迟的微小差异而产生截然不同的结果。这使得传统的"打日志看错误"的调试方式远远不够。开发者需要的是一套能够透视整个系统的三层可观测性体系：基础日志用于问题定位，结构化埋点用于行为分析，分布式追踪用于性能诊断。然而，这一体系面临一个核心矛盾——获取充足的诊断数据与保护用户隐私之间存在天然的张力。数据越丰富，定位问题越容易，但代码片段、文件路径、工具调用细节都可能暴露用户的业务逻辑。这个矛盾贯穿整个遥测系统的设计。

解决方案是一条从本地日志到全局评测的完整链路：原始日志在终端本地落盘，结构化事件经去隐私化后路由到后端分析平台，分布式追踪通过 OpenTelemetry 标准协议导出，Perfetto 格式用于细粒度性能剖析，最终所有数据与 SWE-bench 等评测框架对齐以持续衡量模型能力改进。

---

## 日志基础设施

日志是遥测体系的第一层，也是最基础的保障。项目实现了三套互为补充的日志机制。

错误日志采用 Sink 模式设计。系统在初始化阶段尚未准备好日志后端时，错误不会丢失——它们被排入内部队列暂存，直到 `attachErrorLogSink()` 被调用时才正式接入处理管道。这个附加操作是幂等的，多次调用不会产生重复订阅。一旦 Sink 就绪，每条错误会同时路由到三个目的地：debug 日志文件、内存中的环形缓冲区（保留最近 100 条记录）、以及持久化错误日志文件（仅面向内部用户）。在某些环境下——比如使用 Bedrock、Vertex 或 Foundry 等第三方 Provider 时，或者 `DISABLE_ERROR_REPORTING` 被设置时——错误上报会被完全禁用，以避免将用户流量错误地路由到 Anthropic 后端。

Debug 日志系统则提供了更细粒度的控制。日志级别从 verbose 到 error 共五档，通过 `--debug` 或 `-d` 命令行标志、`DEBUG` 或 `DEBUG_SDK` 环境变量激活。输出格式为结构化的 JSONL——每行一个带时间戳和级别标记的日志条目。在 `--debug` 模式下日志同步写入以确保实时性，非调试模式下则使用带缓冲的写入器，每 1 秒刷新一次。写入器内部维护一个最大 50 条记录的缓冲队列，避免高频日志对 I/O 造成压力。系统还维护一个符号链接指向当前会话的日志目录，方便开发者快速定位最新日志。

会话活动追踪通过引用计数加心跳定时器的方式工作。系统记录 `api_call` 和 `tool_exec` 两类活动，每 30 秒触发一次 keep-alive 信号。这个机制不仅用于诊断空闲超时问题，还为远程控制场景提供了会话存活性的判断依据。所有活动日志在输出前已剥离个人身份信息。

## 结构化埋点（Analytics）

如果说日志是"发生了什么"的原始记录，那么结构化埋点就是对"用户在使用过程中表现出什么行为模式"的系统性观察。这套系统最突出的设计特征是一组环环相扣的模式，共同解决了诊断数据与隐私保护的矛盾。

架构上采用 Queue-then-Drain Sink 模式。与分析事件相关的模块是项目中为数不多的无依赖模块——这个设计决策直接针对循环引用的痛点。任何模块都可以安全地导入 analytics 模块并记录事件，而不必担心破坏依赖图。事件在 Sink 附加之前排队等待，并通过 `queueMicrotask()` 在下一个微任务中排空，从而将启动延迟降到最低。这意味着启动路径上的第一个事件不会因为等待 Sink 初始化而阻塞。

最值得关注的设计是 PII-by-Design 类型系统。TypeScript 的类型系统被巧妙用作为一种"隐私契约"：`AnalyticsMetadata_I_VERIFIED_THIS_IS_NOT_CODE_OR_FILEPATHS` 被声明为 `never` 类型，意味着任何试图将代码片段或文件路径赋值给它的操作都会在编译时报错。开发者必须显式确认某个属性不包含敏感信息才能通过类型检查。另一类型 `AnalyticsMetadata_I_VERIFIED_THIS_IS_PII_TAGGED` 同样为 `never` 类型，用于标记那些明确包含个人身份信息、仅限特权访问的属性。这种设计将隐私审查从运行时的事后审计提前到了编译时的前置约束。

每个事件在发出后进入双后端路由。Datadog 接收去隐私化后的轻量负载——所有 `_PROTO_*` 前缀的 PII 键在这里被剥离；1P BigQuery 则接收完整负载，包含 PII 标记字段，仅供内部有权限的团队分析。Datadog 端还设置了一道严格的白名单关卡：仅有 68 个预定义事件名可以进入 Datadog 管道，其他事件被静默丢弃。基数控制同样严格——用户被映射到 30 个固定桶中（通过 SHA256 哈希），用于支持去重计数而不暴露用户身份；MCP 工具名被归一化为字符串 `"mcp"`；外部模型名映射为规范短名称；版本号被截断为基础版号和发布日期。Datadog 的批处理策略是每批次最多 100 条记录，每 15 秒刷新一次，同时支持优雅退出时的最终刷新。

每个事件在发送前还会经过元数据丰富环节。系统自动附加模型信息（模型名、类型、beta 标记）、会话信息（会话 ID、用户类型、订阅类型）、环境信息（平台、架构、运行时版本、终端类型、CI 标识、WSL 标识）、性能数据（运行时长、内存使用、CPU 占用），以及代理信息（swarm 协作模式、子代理、独立代理标识）。评测相关的 SWE-bench 运行标识也会注入其中。值得注意的是，所有元数据的值类型被限定为布尔值、数字或未定义——字符串类型被完全禁止，从根本上杜绝了代码片段通过元数据字段泄漏的可能性。用户自定义的插件名、技能名和文件路径在发送前都会通过 SHA256 哈希处理。

## OpenTelemetry 三信号追踪

可观测性的第二层是通过 OpenTelemetry 标准协议实现的 Metrics（指标）、Logs（日志）、Traces（追踪）三信号体系。它通过 `CLAUDE_CODE_ENABLE_TELEMETRY` 环境变量激活，支持优雅关闭（默认超时 2000 毫秒），并兼容代理和 mTLS 配置。

指标通过 OTLP 协议导出，支持 gRPC、HTTP 和 Protobuf 三种传输方式，同时支持 Console 输出和 Prometheus 拉取。项目还实现了一个自定义的 BigQueryMetricsExporter，将指标直接写入 BigQuery。指标默认导出间隔为 60 秒。日志信号同样通过 OTLP 导出器发送，默认导出间隔为 5 秒，事件域限定为 `com.anthropic.claude_code.events`。追踪信号的导出间隔同样为 5 秒，分为标准追踪和 Beta 追踪两层。

Span 类型系统定义了六种跨度：`interaction` 作为用户请求周期的根跨度，`llm_request` 跟踪每一次模型调用，`tool` 和它的子类型 `tool.blocked_on_user` 及 `tool.execution` 描述工具执行的完整生命周期，`hook` 用于框架钩子的执行追踪。系统通过两个 AsyncLocalStorage 实例维护上下文传播：`interactionContext` 承载用户请求周期的根跨度，`toolContext` 承载工具执行的嵌套跨度。这两个上下文的隔离确保了并发交互和并行工具调用不会互相干扰。

Span 的管理采用双层存储策略。`activeSpans` 是一个从字符串键到 WeakRef 的映射——弱引用的使用允许垃圾回收器在 Span 不再被引用时自动回收内存，避免了长时间会话中的内存泄漏。`strongSpans` 则维护那些生命周期跨越 AsyncLocalStorage 边界的 Span 的强引用。TTL 清理任务每 60 秒执行一次，驱逐超过 30 分钟的过期 Span，同时清理那些目标已被回收的失效 WeakRef。关键的 Span 操作包括启动和结束交互、模型请求、工具调用和钩子执行，每个操作都会记录与其类型相关的属性——比如模型请求记录输入输出 token 数、缓存命中情况和耗时，工具调用记录工具名和结果。

Beta 会话追踪是一套独立的追踪系统，面向更详细的内容分析。它通过基于哈希的去重机制避免重复记录相同内容——系统提示、消息体和工具定义均通过 SHA256 哈希来识别重复。每个查询源维护一个 `lastReportedMessageHash`，每次只发送自上次报告以来新增的消息。可见性规则区分了访问级别：系统提示和模型输出对全员可见，而思考过程输出仅限内部。内容截断限制为 60KB，与 Honeycomb 平台的 64KB 限制对齐，防止超长内容被静默丢弃。

## Perfetto 性能追踪

Perfetto 追踪是项目中最为精细的性能诊断手段。它仅通过 `PERFETTO_TRACING` 特性开关对内部用户开放。输出格式为 Chrome Trace Event 格式的 JSON，可以在 `ui.perfetto.dev` 或 Chrome 浏览器的 `chrome://tracing` 中直接加载查看。

它最突出的能力是代理层级可视化。在多代理协作场景中，父代理和子代理之间的调用关系通过独立的进程 ID 和线程 ID 在 Perfetto UI 中呈现为清晰的层级关系。每个代理被分配独立的视觉通道，开发者可以直观地看到哪个子代理在什么时间点被调用、执行了多长时间、以及调用结果。

系统还会自动计算三类关键性能指标：每秒输入 token 数、每秒输出 token 数和缓存命中率。每个 API 调用的重试过程也会被记录为子跨度，在 Perfetto UI 中可视化。为防止内存溢出，事件总数上限为 100,000 条——超过上限时丢弃最旧的一半，保留最新的数据。系统支持周期性的全量写入，以及进程退出时的优雅关闭。

## 评测对齐与成本追踪

遥测体系的最终目标是将运行时数据与评测框架对齐，形成持续改进的闭环。SWE-bench 的集成是实现这一闭环的关键——所有分析事件的元数据中都携带 `sweBenchRunId`、`sweBenchInstanceId` 和 `sweBenchTaskId`，使评测团队可以在任意维度上筛选和聚合数据，将模型在标准基准上的表现与真实用户行为关联起来。

Shot 统计从工具调用结果中提取归因信息，识别是第几次尝试成功的（"N-shotted by"模式）。跨会话聚合时按父会话去重，避免子代理的多次尝试被重复计数。Unary 事件日志记录编辑完成类型和用户的接受或拒绝行为，为编辑质量评估提供数据基础。

成本追踪是面向运营和产品决策的重要模块。模型定价定义了六个层级，覆盖从 Haiku 到 Opus 的所有模型变体——包括标准模式和快速模式。成本计算按 token 数乘以单价，同时考虑缓存读写和网络搜索费用。会话级别的成本累积按模型分别统计 token 使用量和美元成本，并递归包含 Advisor 模型的成本。累积结果持久化到项目配置文件中，包含成本、API 耗时、工具耗时、代码行变更量、帧率和模型使用明细。进程退出时，格式化总成本会自动打印到终端。

使用统计聚合通过增量磁盘缓存实现——当天数据始终实时可查。追踪维度包括总会话数、消息数、活跃天数、每日模型 token 消耗、最长会话、模型使用明细、峰值活动时段、推测节省时间和 Shot 分布。这些统计为产品决策提供了从宏观使用趋势到微观行为模式的完整视角。

## 设计模式总结

回顾整个遥测体系，可以提炼出五个贯穿始终的设计模式。

Queue-then-Drain Sink 模式解决了模块初始化顺序问题。错误日志和分析事件都采用这种先排队、后排空的方式，确保启动阶段的事件不会丢失，同时不因等待后端就绪而阻塞启动流程。Sink 附加操作的幂等性保证了系统状态的一致性。

PII-by-Design 模式利用 TypeScript 的类型系统将隐私保护从运行时前置到编译时。通过 `never` 类型声明敏感字段、限制元数据值的类型为原始类型、对用户自定义名称进行哈希处理——这些措施共同构成了一道让开发者几乎不可能意外泄漏用户数据的类型防线。

双后端路由模式解决了不同数据消费者的需求差异。Datadog 面向全体用户，数据去隐私化后提供宏观趋势分析；1P BigQuery 面向内部特权团队，保留完整数据以支持深度调查。一次写入、两路分发，既不重复劳动，也不牺牲安全。

Feature Flag 全链路门控模式确保每个可观测特性都受构建时和运行时双重控制。构建时的 `feature()` 函数允许 Tree-shaking 移除不需要的特性代码，运行时的动态配置则支持面向特定用户群（如内部用户）的灰度发布。

增量上下文模式优化了大规模数据传输的效率。Beta 追踪系统通过消息哈希跟踪来避免重复发送已记录的内容，仅传输新增或变化的上下文数据，在网络传输和后端存储两个维度上降低了成本。

## 小结

本章从日志基础设施出发，逐层深入 Claude Code 的三层可观测性体系。基础日志确保了"出了问题能定位"，结构化埋点回答了"用户在使用什么模式"，OpenTelemetry 三信号追踪提供了"性能瓶颈在哪里"的答案，Perfetto 可视化将代理协作的时序关系呈现为直观的层次图。贯穿其中的隐私保护机制——从类型系统的 PII-by-Design 到双后端路由、再到元数据值的类型限制——展示了在 AI 编码工具这一高度敏感的场景下，如何在不妥协诊断能力的前提下保护用户数据。评测对齐和成本追踪则将遥测数据从技术运维的工具提升为产品决策的依据，形成了从数据采集到价值反馈的完整闭环。
