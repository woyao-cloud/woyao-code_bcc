# 第三章：上下文管理

## 问题背景

Claude Code 作为一款面向终端用户的交互式编程助手，其核心使用场景是**长对话**。用户可能在一次会话中连续提出几十甚至上百个问题，从代码审查到架构设计，从调试排错到重构迁移，对话轮次不断累加。每一次对话都会产生新的消息——用户的问题、模型的回答、工具的调用结果——这些内容的 token 数量呈线性增长。

然而，大语言模型的上下文窗口是固定的。无论是 200K tokens 的标准窗口，还是 1M tokens 的扩展窗口，终究有一个不可逾越的上限。这构成了一对核心矛盾：**对话长度持续增长，而上下文窗口固定不变**。如果不加管理，当累积的 token 超过窗口上限时，API 将返回 `prompt_too_long` 错误，对话被迫中断，用户的体验将急剧下降。

这个问题的本质，就像往一个容量固定的杯子里不断倒水。每次对话都往里加水，杯子总有满溢的一天。管理上下文的关键，就是在水即将溢出时，倒掉一些"旧水"，腾出空间给"新水"。但倒掉哪些水、倒多少、什么时候倒，需要一套精密的机制来决策。

Claude Code 实现了一套**五层压缩策略 + 八级截断优先级链**的多层上下文管理机制。这套体系确保了即使经过上百轮对话，用户也不会因为上下文耗尽而被迫中断工作流。

## Token 追踪与计量

在讨论压缩之前，必须先理解如何衡量上下文的"水位"。Claude Code 中的核心计量函数是 `tokenCountWithEstimation()`，它采用一种**从最新消息向后遍历**的策略。

具体来说，系统从消息列表的末尾开始向前扫描，定位最后一条携带了 `usage` 数据的 Assistant 消息。对于并行工具调用——即多个工具在同一轮被触发的情况——系统会回退到第一个兄弟消息（拥有相同的 `message.id`），以确保交错的 `tool_result` 也被正确计入。计量公式是两部分之和：已记录的使用数据加上对剩余新消息的粗略估算。

Token 消耗由四个部分组成：
- **输入 tokens**（`input_tokens`）：用户发送给模型的消息
- **缓存创建 tokens**（`cache_creation_input_tokens`）：首次写入缓存时消耗
- **缓存读取 tokens**（`cache_read_input_tokens`）：命中缓存时消耗
- **输出 tokens**（`output_tokens`）：模型生成的内容

上下文窗口大小的确定也不是一刀切的。`getContextWindowForModel()` 函数实现了一条七级优先级链，从最高优先级到默认值依次为：

1. `CLAUDE_CODE_MAX_CONTEXT_TOKENS` 环境变量——内部调试人员可以手动指定
2. 模型名称中的 `[1m]` 后缀——显式选择加入 1M 超大上下文
3. 模型能力查找表——根据模型类型自动匹配
4. Beta 请求头中的 `CONTEXT_1M_BETA_HEADER`
5. A/B 实验标志 `getSonnet1mExpTreatmentEnabled()`
6. 内部模型配置
7. 默认值：200,000 tokens

这条优先级链的设计确保了灵活性：高级用户可以通过环境变量或模型后缀手动控制，普通用户则由系统自动选择最合适的窗口大小。

## 五层压缩策略

当系统检测到上下文水位接近窗口上限时，会依次尝试五层压缩策略。这些策略按执行顺序排列，每一层都在前一层不足以解决问题时触发。

### Session Memory Compact（会话记忆压缩）

这是**优先尝试**的压缩策略，在标准压缩之前执行。它的目标不是压缩整个对话，而是智能裁剪 Session Memory（会话记忆）的内容。Session Memory 是模型在当前对话中积累的关于用户的记忆信息，包含偏好、项目上下文等。裁剪的范围控制在 10,000 到 40,000 tokens 之间：低于 10K 则不再压缩，以避免丢失关键记忆；高于 40K 则最多压缩到 40K，以确保腾出足够空间。

这种设计背后有一个精妙的考量：Session Memory 中往往包含大量对当前和后续对话仍然有用的信息，直接交给模型做摘要压缩，比简单地丢弃整条消息更为智能。因此它被优先执行。

### Auto Compact（自动压缩）

Auto Compact 是**主动触发**的压缩策略。它不是在上下文已经满溢时才出手，而是在接近阈值时就提前行动。

它的工作方式可以类比为智慧的水库调度：不是等到大坝即将溃堤才开闸泄洪，而是根据上游来水量提前预判，主动调节水位。

Auto Compact 有几个关键设计：

**缓冲区随窗口大小缩放**。缓冲区大小在 13,000 到 50,000 tokens 之间浮动，窗口越大，缓冲区越宽裕。这确保了小窗口下不至于过早压缩，大窗口下也不必等到危机时刻才行动。

**断路器机制**。如果连续 3 次压缩都失败，系统会停止自动压缩。这防止了在某种异常状态下反复尝试却徒劳无功的情况。

**预测性检查**。`estimateMaxTurnGrowth()` 函数会预估下一轮对话可能增长多少 tokens。如果预估增长量加上当前水位仍然安全，系统会选择暂不压缩，避免不必要的操作。

**恢复关键文件状态**。压缩不是简单的"删掉旧内容"。在执行压缩后，系统会恢复最多 5 个关键文件的状态信息，每个文件 5K tokens，总预算 50K tokens。同时还会保留 Skills 摘要（25K tokens）。这确保了模型在压缩后仍然掌握对话中涉及的核心代码文件状态。

压缩的执行流程是一套完整的流水线：先执行 Pre-Compact 钩子，然后构建压缩 Prompt 并调用模型生成对话摘要，存储压缩边界标记，最后恢复关键文件状态。如果压缩请求本身因为上下文过大而失败，还有专门的 CC-1180 处理逻辑——迭代丢弃最旧的 API 轮次组，最多重试 3 次。

### Snip Compact（裁剪压缩）

Snip Compact 是一种**基于 UUID 的消息移除机制**。它的工作方式最为直接：找到对话中最后一条 `snip_boundary` 系统消息，然后根据 `removedUuids` 集合过滤掉对应的消息。

这里的核心思想是让模型自己决定哪些消息可以删除。当对话到达 30 条消息的提示阈值时，系统会提示模型考虑进行 snipe 操作。模型可以在回答中嵌入 snip_boundary 标记，系统随后据此执行裁剪。

Token 估算采用保守策略：字符数除以 4 约等于 token 数。这种保守估算确保了不会因为低估而意外超出窗口上限。

### Micro Compact（微压缩）

Micro Compact 有两个变体，分别应对不同的场景：

**基于时间的 Microcompact**。当当前时间距离上一条 Assistant 消息的时间间隔超过阈值时触发。它会清空可压缩工具结果的内容——例如 Read 工具读到的文件内容、Bash 命令的输出、Grep 的搜索结果、Web 抓取的页面内容等。这些工具结果往往体量巨大，但很多已经不再需要。系统会保留最近的 N 条结果，确保当前对话轮次仍然有足够的上下文。

**基于缓存的 Microcompact**。这是更高级的变体，使用了 Cache 编辑 API。它的独特之处在于：移除工具结果时**不破坏已经缓存的前缀**，也**不修改本地的消息内容**。这意味着下一次 API 调用时，大部分缓存的上下文仍然可以命中，既节省了 token 又保持了响应速度。

### Reactive Compact（响应式压缩）

当所有主动压缩策略都没能阻止上下文溢出时，API 会返回 `prompt_too_long` 错误。Reactive Compact 就是针对这种紧急情况的**轻量回退方案**。

它是整个压缩体系中的最后一道主动防线。整个模块由 `REACTIVE_COMPACT` 功能开关控制，且每轮最多尝试一次（`hasAttempted` 守卫防止无限重试）。它的任务不是做优雅的摘要，而是以最快的速度压缩上下文，让对话能够继续。

## CLAUDE.md 四级层级加载

CLAUDE.md 是 Claude Code 的项目级指令文件系统，它为模型提供关于项目的关键上下文信息。这套加载体系有明确的层级和优先级。

### 加载顺序

系统按照优先级从低到高的顺序加载 CLAUDE.md 文件，高优先级的文件会覆盖或补充低优先级文件的内容：

1. **Managed memory**（`/etc/claude-code/CLAUDE.md`）：全局企业策略，由系统管理员维护
2. **User memory**（`~/.claude/CLAUDE.md`）：用户个人的全局配置，适用于所有项目
3. **Project memory**（`CLAUDE.md`、`.claude/CLAUDE.md`、`.claude/rules/*.md`）：签入代码库的项目级指令
4. **Local memory**（`CLAUDE.local.md`）：本地私有配置，通常被 `.gitignore` 排除
5. **Auto memory**（`~/.claude/projects/<slug>/memory/`）：系统自动持久化的记忆，从对话中学习而来
6. **Team memory**：团队共享上下文（由 `TEAMMEM` 功能开关控制）

### 目录遍历策略

`getMemoryFiles()` 函数从当前工作目录开始**向上遍历到根目录**。遍历过程中，靠近根目录的文件先被加载（优先级低），靠近当前工作目录的文件后被加载（优先级高）。这意味着越接近用户当前工作位置的文件，其指令权重越高。

还有一个精妙的细节：当使用嵌套 Git Worktree 时，系统会检测并跳过主仓库的 Project 文件，避免重复加载。

### 高级特性

**@include 指令**。Memory 文件可以通过 `@include` 引用其他文件，支持三种路径解析方式：`@path`（相对于某个基准目录）、`@./path`（相对于当前文件）、`@~/path`（相对于用户主目录）。最深嵌套层级为 5 层，且有循环引用检测。

**条件规则**。`.claude/rules/*.md` 文件可以通过 frontmatter 的 `paths` 字段实现路径范围限定。只有当用户操作的文件匹配某个 glob 模式时，对应的规则才会被加载。这让规则可以精确作用于特定目录或文件类型。

**文件内容截断**。单个 Memory 文件的内容上限为 40,000 字符（`MAX_FILE_CONTENT_LENGTH`）。超过上限的内容会被截断，以防止某个文件独占大量上下文。

## 上下文组装优先级

最终发送给模型的 Prompt 不是简单地把所有内容拼接在一起，而是按照严格的优先级结构组装。这就像建造一座建筑，不同的材料有各自的承重角色。

### 最终 Prompt 结构

```
1. 归属头 + CLI Sysprompt 前缀 —— 可缓存前缀
2. 基础 System Prompt
3. System Context（Git 状态等）
4. Advisor 指令（如启用）

5. <project-instructions> CLAUDE.md 所有层级
    → 高权重：携带 "OVERRIDE" 声明
6. <system-reminder> currentDate 等
    → 低权重：仅作参考，"可能相关"

7. 对话历史

8. 附件消息（Memory/Skills/MCP）
9. Hook 结果
```

### 关键设计原则

**CLAUDE.md 高权重注入**。CLAUDE.md 的内容被放入 `<project-instructions>` 标签，并携带 "OVERRIDE" 声明。这意味着模型会把这些内容视为必须遵守的指令，而不是"仅供参考"的辅助信息。这是确保项目级规则被严格执行的关键设计。

**环境上下文低权重**。日期、路径等环境信息被放入 `<system-reminder>`，模型会将其视为可能相关的参考信息，但不会像对待指令那样必须遵守。

**压缩后消息顺序**。经过压缩后，消息的顺序为：压缩边界标记 → 压缩摘要消息 → 保留的原始消息 → 附件 → 钩子结果。这个顺序确保了模型能先看到压缩后的摘要作为上下文，再处理当前轮的对话。

## 八级截断优先级链

当所有五层压缩策略都已用尽，但上下文仍然超限时，系统进入**八级截断优先级链**。这是一套由浅入深的应急方案，每个级别都比前一级更为激进。

| 级别 | 策略 | 机制 |
|------|------|------|
| 1 | 工具结果预算 | 截断或持久化单个工具结果到磁盘 |
| 2 | Snip | 基于 UUID 移除最旧消息 |
| 3 | Microcompact | 基于时间或缓存清空旧工具结果 |
| 4 | AutoCompact | 完整对话摘要化（阈值触发） |
| 5 | ReactiveCompact | API 错误后的紧急摘要 |
| 6 | PTL Retry | 压缩请求自身的组级删除 |
| 7 | Output Token Recovery | 升级 max_tokens 上限（8K → 64K） |
| 8 | 阻塞限制 | 返回合成错误，保留 `/compact` 余量 |

前五级实际上就是前面介绍的五层压缩策略，它们在截断优先级链中再次出现，体现了"层层递进、逐渐升级"的设计哲学。

### PTL Retry（重试中的组级删除）

当压缩请求本身因为上下文过大而无法执行时（即压缩请求的 Prompt 也触发了 `prompt_too_long`），PTL Retry 机制会被激活。系统会迭代地丢弃最旧的 API 轮次组，最多重试 3 次。如果 3 次后仍然失败，回退方案是丢弃 20% 的组。但有一个底线：**永不丢弃到低于 1 组**，确保对话不会完全丢失上下文。

### Output Token Recovery（输出 Token 恢复）

这是一个非常巧妙的策略：当输入上下文已经无法再压缩时，系统会反过来扩大输出 token 的上限（从默认的 8K 提升到 64K）。这虽然没有直接解决输入过长的问题，但至少确保了模型有足够的空间生成完整的回答，而不是在回答中途被截断。

### 阻塞限制（最后防线）

这是整个截断链的**最后一道防线**。当自动压缩被关闭，且上下文窗口剩余不足 3,000 tokens 时，系统会直接返回合成的 `prompt_too_long` 错误，而不实际调用 API。

这 3,000 tokens 的保留空间（`MANUAL_COMPACT_BUFFER_TOKENS = 3000`）是留给用户手动执行 `/compact` 命令的"救命稻草"。如果没有这个保留，系统会把最后一点 token 也用尽，用户连执行 `/compact` 的空间都没有了，对话就真的无法挽救了。

## 文件历史快照

上下文管理不仅仅是压缩对话，还包括**保护用户的工作成果**。当系统压缩或删除某些消息时，其中可能包含了用户或模型对代码文件的修改记录。文件历史快照机制就是为了应对这个问题。

### 快照机制

查询引擎在每次 API 调用前都会拍摄文件历史快照。这个流程分为三个阶段：

1. **捕获阶段**：获取当前文件历史状态，记录哪些文件被跟踪、哪些被修改过
2. **异步 IO 阶段**：对修改过的跟踪文件进行备份。使用 `copyFile` 提高效率，通过 mtime（修改时间）优化后按需比较文件内容，避免不必要的磁盘写入
3. **提交阶段**：将新快照提交到状态中。未修改的文件直接继承上一个快照的备份引用，避免重复备份

### 关键参数

- 快照环形缓冲区：最多保留 20 个快照（`MAX_SNAPSHOTS = 20`）
- 备份路径：`~/.claude/file-history/{sessionId}/{sha256_16chars}@vN`
- 支持 `fileHistoryRewind()` 函数，可以将文件系统回退到历史快照状态

环形缓冲区的设计意味着系统始终保留最近的 20 个快照，既不会无限膨胀占用磁盘空间，也提供了足够的回退深度。当用户在对话中频繁修改文件时，即使某个修改被上下文压缩"遗忘"了，仍然可以通过文件历史快照找回。

## 小结

Claude Code 的上下文管理是一套精密的多层体系。从最前端的主动压缩到最后的阻塞限制，每一层都在扮演特定的角色：

**五层压缩策略**是"软性"手段，它们在上下文溢出之前以智能的方式腾出空间。Session Memory Compact 裁剪记忆但保留精髓，Auto Compact 预判水位并主动泄洪，Snip Compact 让模型自己决定哪些可以丢弃，Micro Compact 在不破坏缓存的前提下清理工具结果，Reactive Compact 作为紧急情况下的轻量回退。

**八级截断优先级链**是"硬性"手段，它们在压缩不足以解决问题时逐级升级。从工具结果预算到阻塞限制，每一级都比上一级更激进，但始终保留手动 `/compact` 的最后空间。

**CLAUDE.md 层级加载**和**上下文组装优先级**确保了模型获得的信息在质量和权重上都有合理的分层。高权重的项目指令和低权重的环境信息被区别对待，压缩后的消息顺序也被精心设计。

**文件历史快照**则是一张安全网，确保即使在激进的压缩之后，用户的核心工作成果仍然有迹可循。

整体来看，这套机制的核心哲学是：**尽可能不让用户感知到上下文管理的存在**。所有的压缩、截断、快照都在后台自动完成，用户只需继续对话即可。只有当所有自动手段都失效时，系统才会通过阻塞限制"告知"用户——而此时，仍然保留了手动 `/compact` 的空间。

这就像一个有经验的管家：他会在房间变得杂乱之前悄悄整理，在客人注意到之前就已经处理好了。只有在万不得已时，他才会礼貌地提醒客人需要稍微腾挪一下空间。
