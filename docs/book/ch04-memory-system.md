# 第四章：记忆系统

## 问题背景

每一次与 AI 编程工具的对话，都始于一个"空状态"——模型没有关于你的项目、你的工作方式、你的偏好的任何信息。它不知道你习惯用哪种测试框架，不知道你的团队约定是什么，不知道上周你刚刚踩过的那个坑。这种"每次从头开始"的体验，就像你每天都在同一个工位上办公，但每天早上所有的文件、笔记和工具都会被清空一样荒谬。

记忆系统要解决的正是这个问题：如何让 AI 编程助手在会话之间记住有价值的信息，并且让这些信息自然地融入每一次交互，而不需要用户反复重复同样的背景和偏好。

这个系统的完整闭环是：会话记忆在每轮对话结束时被自动提取，经过离线阶段的巩固和优化，最终转化为行为反馈和指令注入，在后续会话中持续发挥作用。四个环节环环相扣，形成了一条从"瞬时记忆"到"长期行为准则"的完整流水线。

## 跨会话持久化记忆

### 存储路径的优先级

记忆文件存放在用户机器上的特定目录中。系统通过三级优先级确定最终存储位置：首先检查是否有环境变量 `CLAUDE_COWORK_MEMORY_PATH_OVERRIDE` 指定了完整路径覆盖，这通常用于测试或特殊部署场景；其次检查配置项中的 `autoMemoryDirectory` 字段，用户可以分别在用户级、项目级或策略级配置中指定；如果前两者都没有设置，则使用默认路径——在 `~/.claude/projects/` 目录下，以经过规范化的 Git 根目录路径作为子目录名。

这里有一个值得注意的细节：Git 根目录的规范化处理确保了同一个仓库的不同 Worktree 共享同一套自动记忆目录。无论你在哪个 Worktree 中工作，记忆都是共通的。

### 四种记忆类型

系统将记忆分为四种类型，每种类型服务于不同的目的。用户类型记录的是用户的角色、目标、职责和知识水平——比如"我是一个前端开发者，主要使用 React 和 TypeScript"。反馈类型记录的是关于工作方式的用户指导，既包括失败时的纠正，也包括成功时的确认——比如"不要 mock 数据库，我们使用真实实例进行集成测试"。项目类型跟踪项目的进展、目标、Bug 和时间线——比如"当前 Sprint 的目标是完成支付模块的重构"。引用类型则保存外部系统的位置引用——比如 Linear 上的某个 Issue 链接、Grafana 监控面板的地址、Slack 频道的入口。

这四种记忆各自独立存储，每个记忆是一个独立的 Markdown 文件，通过文件的元数据头部标明类型、名称和一句摘要描述。这种结构既清晰又灵活——每个记忆都可以独立创建、更新和删除，而摘要描述则用于后续的语义相关性判断。

### MEMORY.md 索引

所有的记忆文件由一份索引文件 `MEMORY.md` 统一管理。这份索引本身并不是一条记忆，而是一个清单，每行以列表形式列出一条记忆的标题、文件名和一行摘要。它有两个硬性约束：最多 200 行，最大不超过 25KB。每次会话开始时，系统会自动将这份索引加载到模型的初始上下文中，让模型一"醒来"就知道当前有哪些可用的记忆。

### 记忆新鲜度

记忆是有保质期的。系统会跟踪每条记忆的年龄，超过一天没有更新的记忆会被附加"新鲜度警告"。这个机制帮助模型判断一条记忆的信息是否仍然有效——如果用户上周说过"我们正在评估使用 Bun 替代 Node.js"，而这条记忆已经过了一周没有更新，模型就知道需要谨慎对待这条信息，或者主动询问用户最新的进展。

## 自动提取机制

### 提取时机

在每一轮对话的末尾，当模型产出了最终响应并且没有发起任何工具调用时，系统会启动一个 Fork 子代理来执行记忆提取。这个子代理专门负责分析本轮对话中新增的消息，判断其中是否有值得保存为长期记忆的信息。

### 多重门控

提取并不是每次对话都会触发的。系统设置了多层门控条件来精确控制何时启动提取：需要对应的 Feature Flag 在构建时启用；只有主代理会触发提取，子代理不会；有一个集中的开关可以完全禁用提取功能；穷鬼模式下不会执行提取（因为这会消耗额外的 Token）；自动记忆功能本身需要被用户启用；远程模式下不执行提取；如果主代理在本轮中自己写入了记忆文件，自动提取也不会再重复执行。

这些门控条件层层递进，确保提取只在最合适的时机发生，既不会过度消耗资源，也不会干扰用户的正常使用。

### 权限控制

提取代理拥有一个精心设计的权限范围：它可以无限制地使用 Read、Grep 和 Glob 工具来读取和分析文件；Bash 工具仅限只读命令，不能执行任何修改操作；Edit 和 Write 工具只能操作自动记忆目录内的路径，不能触及项目中的其他文件；除此之外的所有工具都被直接拒绝。

这种权限设计体现了"最小必要"原则：提取代理需要读取足够的信息才能做出判断，但它的写操作被严格限定在记忆目录之内，防止意外修改项目文件。

### 效率策略

提取代理的工作分两个阶段完成。第一轮它读取所有现有的记忆文件，了解当前已经有哪些记忆；第二轮它根据分析结果写入新的记忆或更新已有的记忆。每次运行最多执行五轮交互。此外，系统通过配置控制提取的频率——默认情况下每次符合条件都会提取，但可以根据需要调整为每 N 轮执行一次，以平衡提取效果和 Token 消耗。

## Auto-Dream 离线巩固

### 系统定位

Auto-Dream 是记忆系统的后台巩固模块。如果说自动提取是在线阶段"捕获"新的记忆素材，Auto-Dream 则是在用户不活跃时对这些素材进行"精加工"——整合冗余信息、优化记忆结构、删除过时的内容、更新索引文件。

### 三重门控

进入离线巩固需要通过三道门。第一道是时间门：距离上次巩固必须超过最小时间间隔，默认是 24 小时。第二道是会话门：自上次巩固以来，累积的对话记录数量必须达到最低要求，默认是 5 条。第三道是锁门：确保没有其他进程正在执行巩固操作。

这三道门分别从时间频率、信息积累量和并发安全三个维度保证了巩固操作的质量和安全性。

### 锁机制

锁机制的实现方式很巧妙：在记忆目录中创建一个名为 `.consolidate-lock` 的文件，文件的修改时间就是上次巩固的时间戳，文件内容则记录了持有者的进程 ID。锁的有效期是一小时，超过一小时自动过期。这样既防止了多个进程同时进行巩固操作，也通过过期机制避免了进程崩溃后锁永远无法释放的问题。

### 巩固四阶段

巩固过程分为四个阶段依次执行。第一阶段是定向：系统列出记忆目录中的所有文件，阅读索引文件，浏览各个主题文件，对整个记忆库建立一个全局视图。第二阶段是收集：查阅每日日志，检测已经与当前状态不一致的记忆，精确搜索对话记录文件中与记忆相关的信息片段。第三阶段是巩固：将新的信号合并到已有的主题文件中，将相对日期转换为绝对日期（避免"上周"这样的表述随着时间的推移失去意义），删除已经被后续信息推翻的事实。第四阶段是修剪和索引：更新索引文件，确保它在 200 行和 25KB 的限制之内，移除已经过期的引用。

### 手动模式

除了自动执行，用户也可以通过两条命令手动触发记忆管理。`/dream` 命令交互式运行与自动巩固相同的流程，但拥有完整的工具权限——这意味着它可以执行更深入的分析和更广泛的修改。`/remember` 命令则用于审查所有记忆层，并给出将自动记忆提升为永久指令的建议——比如把某个反复出现的偏好从自动记忆升级到项目级指令文件中。

## Hooks 系统

### 事件类型

Hooks 系统是记忆和指令注入的"神经系统"，定义了二十多种事件类型来覆盖工具调用的整个生命周期。工具在调用前、调用后、调用失败时都会触发对应的事件。用户提交 Prompt 时、会话开始和结束时、模型停止或失败时也各有对应的事件。子代理的启动和停止、对话压缩的前后、发送通知、权限请求和权限拒绝，都有各自的 Hook 事件。

此外，仓库初始化、MCP 发现对话框、设置文件变更、指令文件加载、Worktree 的创建和移除、工作目录和文件的变更，也都在 Hook 系统的覆盖范围之内。

### 命令类型

每个 Hook 事件可以关联六种不同类型的命令。Shell 命令直接执行系统命令；Prompt 命令使用 LLM 评估某个条件是否满足；Agent 命令启动一个代理验证器；HTTP 命令发送 HTTP 请求到指定的端点；Callback 命令执行进程内的 JavaScript 回调；Function 命令执行注册的函数。

每种命令类型都有丰富的配置选项：可以用 `if` 条件指定权限规则语法来精确控制触发条件，可以设置超时时间，可以配置状态提示信息，可以设置为只运行一次的模式。对于 Shell 命令，还支持异步执行和异步唤醒模式。

### 多源配置

Hook 的配置来自多个源头，按优先级从低到高依次是：用户级设置文件、项目级设置文件（会签入代码库，团队成员共享）、本地设置文件（Git 忽略，仅个人使用）、插件注册的 Hook、进程内临时的会话级 Hook、内部注册的内置 Hook，以及企业托管的管理策略。

这种多源配置结构使得 Hook 既可以在团队层面统一管理，又可以灵活地适应个人的特殊需求。

### 执行流程

当某个事件触发时，系统会从所有配置源中汇编出完整的 Hook 列表，按事件类型和条件进行匹配过滤，去重后执行。在交互模式下，所有的 Hook 都需要工作区信任——这意味着项目中的 Hook 配置在用户确认信任之前不会自动执行，这是一个重要的安全设计。

Hook 的执行结果有多种处理方式：如果退出码为 2，代表阻塞错误，系统会注入一条消息到对话中让循环继续；如果返回了更新后的输入，系统会用更新后的数据替换工具输入；如果返回了额外的上下文，这些内容会被注入到下一轮 Prompt 中；如果返回了权限决策，则会覆盖默认的权限处理逻辑。

### Stop Hooks 的特殊地位

Stop Hook 在查询循环中扮演着特殊的角色。在每个模型响应结束时，系统会依次处理 Stop Hook 中的阻塞和预防逻辑，触发后台维护任务（包括 Prompt 建议、记忆提取和 Auto-Dream），最后评估 Token 预算是否满足继续对话的条件。这就像每次对话的"收尾工作"——在模型说完最后一句话之后，系统还要检查一遍该做的事情是否都做了。

## 指令注入流水线

### 多层注入

指令注入是记忆系统发挥作用的关键环节。系统构建了七层指令来源，按优先级从高到低依次注入到模型的上下文中。最高优先级的是托管记忆，通常由企业管理策略控制，位于 `/etc/claude-code/CLAUDE.md`。其次是用户级记忆，来自 `~/.claude/CLAUDE.md` 和规则文件。再往下是项目级记忆，来自项目根目录的 `CLAUDE.md`、`.claude/CLAUDE.md` 和规则文件。然后是本地级记忆，来自 `.claude.local.md`，这通常是个人本地的特殊配置。

后三层则是补充性质的：自动记忆来自 `~/.claude/projects/` 下的 `MEMORY.md` 索引文件，团队记忆则受 Feature Flag 控制。每一层都是在前一层基础上的补充或覆盖，最终形成一个丰富的、多层次的指令系统。

### 优先级链

设置来源的优先级链是：用户设置低于项目设置，项目设置低于本地设置，本地设置低于命令行标志设置，命令行标志设置低于策略设置。后面的源总是覆盖前面的源。用户可以通过 `--setting-sources` 标志选择性禁用某些来源，而策略和标志来源始终被包含。

### 条件规则

项目中的 `.claude/rules/` 目录下的规则文件通过路径限定实现条件加载。每个规则文件的元数据头部可以指定 `paths` 字段，只有当用户当前操作的文件路径匹配指定的 Glob 模式时，该规则才会被激活。这意味着不同的子目录或不同的文件类型可以关联不同的行为规则，而不是所有规则在任何时候都生效。

### 企业托管设置

对于企业用户，系统支持托管设置文件 `managed-settings.json` 和 `managed-settings.d/` 目录下的多个配置文件。这些文件按字母顺序加载，后加载的文件优先级更高。这种设计允许管理团队将不同方面的策略定义在独立的文件中，实现声明式的策略组合，便于分工维护和版本管理。

## 用户偏好学习

### Feedback Memory

反馈类型的记忆是系统学习用户偏好的核心载体。每条反馈记忆的格式包含三个部分：规则本身、原因和如何应用。原因部分解释了这条规则为什么存在——通常是因为过去某个事故或者用户强烈的偏好。如何应用部分则说明了在什么场景下应该应用这条规则。

一个关键的设计原则是：不仅要记录失败时的纠正，也要记录成功时的确认。双重来源让模型能够在正反两个方向上持续精细化自己的行为。比如用户说"不要 mock 数据库"是一条纠正，而用户说"单个打包 PR 的方式是正确的"则是一条确认。两者同样有价值。

### 自动技能改进

系统还实现了一个自动技能改进机制，将用户的偏好学习推向了更高的层次。这个机制监控技能执行过程中用户的纠正和偏好表达，每隔若干轮触发一次分析。它会在用户消息中识别特定的信号模式——比如"添加/修改/删除步骤"、"不，用 X 代替"、"总是使用 Y"——然后自动生成技能更新元数据，通过侧信道 LLM 调用自动重写技能定义文件。

这就是人类反馈到永久技能定义的自动化闭环：用户在一次对话中说"不要用这种方式"，系统不仅记住了这句话，还把它转化成了后续会话中持续起作用的行为准则。

## 小结

记忆系统是 Claude Code CLI 中最复杂的子系统之一，它实现了从会话级瞬时记忆到长期行为准则的完整转化闭环。自动提取机制在每轮对话结束时捕获有价值的记忆素材，离线巩固系统在用户不活跃时对这些素材进行整合和优化，Hooks 系统提供了覆盖整个工具生命周期的神经网络，指令注入流水线将多层记忆和配置注入到每次对话的上下文中，而用户偏好学习机制则让系统能够从每一次交互中持续进化。

这个系统的设计体现了几个核心原则：记忆是有层次的——从会话到自动记忆再到永久指令，每一层的持久化程度和覆盖范围都不同；记忆是有时效的——新鲜度追踪确保模型不会基于过时的信息做决策；记忆是需要保护的——提取代理的权限被严格限定，锁机制防止并发冲突；记忆是需要整合的——离线巩固阶段对记忆进行全局优化而非简单堆积。

最终，这个系统让 AI 编程助手从一个"每次对话都是初次见面"的工具，变成了一位"了解你的工作方式、记住你的偏好、从经验中学习"的伙伴。
