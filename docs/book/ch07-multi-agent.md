# 第七章 多 Agent 协作架构

## 问题背景

单一 Agent 架构在实际使用中面临两个根本性的瓶颈。其一是上下文窗口的有界性——无论模型支持的上下文窗口多大，对话历史总会持续增长，最终达到上限。其二是串行工具执行的吞吐量限制——单 Agent 一次只能执行一个工具调用，对于需要同时探索多个方向的复杂任务，这种串行模式成为性能瓶颈。

为了突破这些限制，项目实现了三种独立的多 Agent 协作模式：Fork 子代理、AgentTool 嵌套和 Coordinator 模式。三者形成互补关系——Fork 追求极致的 Prompt Cache 复用效率，AgentTool 提供通用灵活的子代理创建能力，Coordinator 专注于大规模协调场景中的工作分配与合并。

这三种模式之间存在明确的互斥规则。Coordinator 模式激活时，Fork 子代理被禁用，因为协调器已经承担了全部的编排职责。Fork 路径激活时，所有 Agent 创建操作强制转为异步执行，绕过常规的 Agent 注册机制。常规 Agent 路径则通过类型注册表匹配已注册的代理类型。

## Fork 子代理系统

Fork 子代理的核心设计理念是让多个子任务共享同一个 Prompt Cache 前缀。当多个子节点拥有完全相同的消息前缀时，API 端的 Prompt Cache 命中率被最大化，从而显著降低 Token 消耗。这在需要同时对代码库多个区域进行独立操作的场景中尤其有效。

Fork 子代理的启用需要三个条件同时满足：构建时必须开启 Fork 子代理特性开关，当前不能处于 Coordinator 模式，以及会话必须是交互式会话（不能是 SDK 或管道模式）。这三个条件缺一不可。

为了实现 Cache 共享，Fork 子代理的消息结构经过精心设计。所有子节点的消息前缀完全相同——包含完整的父对话历史、一条完整的 Assistant 消息（含所有 tool_use 块）、以及一条将工具调用统一替换为占位文本的用户消息。这个公共前缀之后才是每个子节点独有的指令文本。由于 Prompt Cache 是基于前缀匹配的，所有子节点的公共前缀部分在 API 端只需计算一次。

系统为递归 Fork 设置了双重保护机制。第一道守卫在入口处检查当前工具调用的来源是否是 Fork 代理内置类型，如果是则拒绝再次 Fork。第二道回退守卫扫描消息中是否存在特定的 Fork 标记标签，作为兜底防护。两道守卫确保不会出现 Fork 嵌套 Fork 的死循环。

Fork 子节点遵循十条不可协商的行为规则。这些规则包括：子节点必须意识到自己是 Fork 子节点，不得再生成子代理；不得对话、提问或建议下一步；如果修改了文件，必须在报告前提交更改；响应必须以特定的前缀格式开头等。这些约束确保了 Fork 子节点的执行简洁高效，不会产生多余的对话轮次。

可选的 Worktree 隔离模式允许子代理在独立的工作目录中操作。系统会附加路径转换通知，指导子代理如何继承和翻译父代理的工作目录路径，并在必要时重新读取文件。

## AgentTool 嵌套

AgentTool 是创建子代理的通用入口。它提供了一套标准化的工具定义，包含完整的权限校验和生命周期管理。工具名称是 Agent（旧别名为 Task）。

AgentTool 的输入 Schema 分为基础参数和扩展参数两层。基础参数包括任务简述、完整任务描述、可选的代理类型和模型覆盖、以及异步执行标志。扩展参数则包括代理名称、团队名称、隔离模式和工作目录覆盖。Schema 字段会根据特性开关动态调整——例如 Fork 开启时隐藏异步执行参数，非特定模式下隐藏工作目录参数。

路由决策逻辑是 AgentTool 的核心。当同时提供了团队名称和代理名称时，走多代理团队路径。否则，系统根据是否提供了代理类型参数以及 Fork 是否开启来决定有效类型。如果进入了 Fork 路径，系统使用内联的 Fork 代理定义，检查递归 Fork 守卫，并从父代理的工具中筛选出 Fork 兼容的工具组成工具池。如果走非 Fork 路径，系统在已注册的活跃代理中搜索匹配的类型，如果被权限规则拒绝则抛出错误并附带来源信息。

每个子代理的工具池都是独立组装的，使用子代理自身的权限模式，完全独立于父代理的工具限制。这意味着子代理可以有不同的工具访问权限。

异步执行判定由多个条件共同决定：工具调用参数中的异步标志、代理定义中的后台执行属性、Coordinator 模式、Fork 路径的强制异步标志、以及助理或特定工作流模式。在 Fork 路径下，所有 Agent 创建操作强制异步执行，统一通过特定的 XML 消息格式进行交互。

上下文边界策略在 Fork 和非 Fork 路径之间存在显著差异。非 Fork 代理从零上下文开始——只接收任务描述作为用户消息，不携带父对话的任何历史。非 Fork 代理被指示为刚走进房间的聪明同事，不知道当前对话的任何上下文。而 Fork 代理则携带父代理的完整对话历史，这是为了实现 Prompt Cache 共享而做出的设计取舍。

## Coordinator 模式

Coordinator 模式的设计理念是将主代理剥离所有实操工具——不允许读文件、写代码或执行命令。协调器只保留编排相关的工具：创建子代理、发送消息和停止任务。协调器不负责执行任何具体工作，只负责委派和管理，所有实际工作由 Worker 代理执行。

Coordinator 模式定义了明确的四阶段工作流。研究阶段由多个 Worker 代理并行执行，负责调查代码库、定位关键文件。综合阶段由协调器自己执行，阅读研究发现并撰写实现规范。实现阶段再次交由 Worker 代理执行针对性的修改并提交。验证阶段由 Worker 代理测试变更是否有效。

Coordinator 最核心的约束是"永远不要委派理解"。反模式的做法是将综合判断推给 Worker 代理，例如说"基于你的发现，修复这个 bug"。正确的做法是协调器先理解研究发现，再写出具体的文件路径、行号和确切的变更描述，让 Worker 代理只做执行。

Worker 代理是续接已有会话还是新建，决策依据是一个五场景矩阵。在需要编辑的确切文件上进行调研时，续接更好，因为上下文已经建立。宽泛调研后转向具体实现时，新建更有利于聚焦。纠正失败时需要续接以保留错误上下文。验证另一个 Worker 的代码时需要新建以获得独立视角。当方法完全错误时也需要新建以获得全新的上下文。

Worker 代理的实现上，其工具集合是异步代理允许的工具集减去内部编排工具，防止递归编排。在 Coordinator 模式下，所有内置代理类型都被替换为 Worker 代理。

Scratchpad 机制实现了跨 Worker 的知识共享。当该功能启用时，Worker 获得一个免权限的读写目录。Worker A 的研究成果可以直接被 Worker B 读取，无需经过协调器中转。这减少了协调器的负担，也提高了并行效率。

Coordinator 模式与 Fork 子代理明确互斥。当系统检测到 Coordinator 模式时，Fork 子代理的启用条件直接返回假。

## 并发子任务

系统明确鼓励并发执行。基本原则是尽可能同时启动多个代理以最大化性能。具体来说，只读任务可以自由并行执行。写重任务需要按文件集串行执行，避免多个代理同时修改同一个文件造成冲突。验证和实现针对不同文件区域时可以并行。

所有的 Fork 模式代理强制异步执行，通过通知队列与主代理通信。通知默认采用较低的优先级，不抢占用户输入。系统支持优先级队列管理，可以根据任务的重要程度调整通知的优先级。

进程内协作提供了一套完整工具集。任务创建、获取、列表和更新工具用于管理任务生命周期。发送消息工具支持代理间的消息传递。定时调度工具用于周期性任务。基于文件锁的并发原语是核心并发控制机制，通过原子获取防止重复分配。

## 通信机制

系统中的代理通信有三种机制。同步工具结果是最基础的通信方式——父代理的 Agent 工具调用阻塞直到子代理完成，结果作为工具结果块返回到当前轮次，父模型在下一轮的上下文中才能看到。

异步任务通知队列用于后台代理。后台代理通过通知队列产出特定的 XML 消息，这些消息作为用户角色消息注入到轮次之间。协调器或父代理通过消息中的特定标签来区分真实用户输入和代理通知。

Mailbox 用于进程内队友之间的通信。它支持定向发送、全体广播、队友完成全部任务时的自动通知，以及队友通过邮箱向领导者请求权限决策。

发送消息工具支持通过代理名称或代理 ID 向运行中或已停止的代理发送后续消息。对于运行中的代理，消息排队到待处理队列，在循环边界交付。对于已停止的代理，系统从侧链记录中恢复并继续执行。

## 工具权限范围控制

子代理的工具权限受多层控制。所有子代理共用的禁用工具列表包含任务输出、计划模式入口和出口、Agent 工具本身、询问用户工具、任务停止工具等工作流控制类工具。

对于异步代理，有一个专门的白名单定义了允许的工具集合，包括文件读取、网络搜索、待办事项写入、内容搜索、网络抓取、全局搜索、Shell 执行、文件编辑和写入等。

Coordinator 模式下的 Worker 代理受到额外限制，被排除了内部编排工具，防止递归编排。自定义代理则在通用禁用列表的基础上有更严格的超集限制。

## Agent 注册体系

系统内置了六种 Agent 类型。通用代理拥有全工具访问权限，是默认的通用代理类型，适用于研究、搜索和多步骤任务。探索代理是只读的文件搜索专家，禁止编辑、写入和创建子代理，使用模型继承或轻量模型回退。规划代理相当于软件架构师，只读规划，同样禁止编辑、写入和创建子代理。此外还有终端状态栏配置代理、Claude Code 使用指导代理，以及经过双重门控的验证代理。

Agent 定义遵循清晰的类型层级。基础定义包含通用字段，如代理类型、工具列表、禁用工具列表、技能、MCP 服务器、钩子、模型、权限模式、最大轮次、隔离模式和是否省略项目说明文档等。内建代理定义在基础定义之上增加了来源标记和系统提示生成方法。自定义代理使用闭包形式的系统提示生成方法，来源标记为用户设置来源。插件代理来源标记为插件，附加插件元数据。

代理的发现和优先级合并遵循明确的规则。系统从内置定义、Markdown 文件目录和插件三个来源加载 Agent 定义。合并时按优先级顺序去重：内建代理优先级最高，其次是插件、用户、项目、策略标志和托管代理。同一代理类型在优先级高的源中定义时，会覆盖优先级低的源中的同名定义。

## 模式选择指南

在具体场景中如何选择多 Agent 模式？对于高度并行的独立读写任务，Fork 是最佳选择，因为 Cache 共享最大化。对于通用的子代理需求，如研究、搜索或实现，AgentTool 的通用代理类型最灵活且类型安全。对于大规模多功能协调场景，Coordinator 模式的角色分离最清晰。对于单步专业任务，如探索或规划，使用 AgentTool 的专用代理类型最合适，类型安全且无上下文污染。

上下文隔离策略因模式而异。Fork 子代理携带父代理的完整上下文，以 Cache 共享为优先。非 Fork 子代理从零上下文启动，只接收任务描述，以隔离为优先。Coordinator Worker 接收协调器提供的具体指令，遵循"永不委派理解"原则。

## 小结

多 Agent 协作架构是突破单 Agent 上下文窗口和串行执行瓶颈的关键设计。Fork 子代理通过共享 Prompt Cache 前缀实现极致的 Token 效率，AgentTool 提供通用的子代理创建能力，Coordinator 模式则为大规模协调提供了清晰的角色分离和四阶段工作流。三种模式各有适用场景，互斥规则确保协作路径清晰。并发执行原则和多种通信机制共同构成了一个灵活高效的多 Agent 协作体系，使得复杂任务可以被拆解、并行和协调，极大地提升了系统的整体处理能力。
