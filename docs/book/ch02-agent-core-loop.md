# 第二章：Agent 核心运行循环

## 问题背景

在传统的编程辅助工具中，交互模式是简单直接的：用户提问，工具回答。无论是搜索文档、生成代码片段还是解释报错信息，都是一次性的请求-响应周期。然而，当 AI 从"回答问题"进化到"完成复杂任务"时，这个模式就暴露了根本性的缺陷——一个真实的开发任务，比如"在现有项目中添加用户登录功能"，需要理解代码库结构、修改多个文件、运行测试验证、根据失败信息修复问题，甚至可能往返多次才能完成。这不可能在一次问答中解决。

问题的本质在于：复杂的工程任务需要多步自主执行的能力。AI 工具不能只是"回答用户的下一个问题"，而必须能够"独立规划和执行一系列操作，在必要时暂停等待用户输入，然后继续"。这就是 Agentic Loop——代理循环——模式诞生的背景。它借鉴了强化学习中"环境-行动-反馈"的循环范式：模型观察当前状态（上下文）、决定下一步行动（工具调用）、执行并观察结果，然后重复，直到任务完成或遇到无法自行解决的障碍。

这个看似简单的循环背后，隐藏着大量的工程复杂性。本章覆盖的五个子系统——消息准备、系统提示组装、流式通信、工具调度和异常兜底——共同支撑着这个循环的稳定运行。在展开每个子系统之前，有必要先理解循环本身的宏观节奏。

整体循环的运行逻辑像一个编排精密的流水线。每一轮迭代从上轮的状态快照开始，经过上下文管理（压缩、裁剪、精简），到系统提示的动态组装，再到阻塞限制检查，然后是流式 API 调用，响应处理（工具执行与结果收集），最后决定是否继续。如果模型产生了工具调用请求（即需要读取文件、执行命令或访问网络），循环就会继续；如果模型直接给出了最终回答，或者触发了预算上限，或者遇到了无法恢复的错误，循环终止。这个"继续还是不继续"的判断是循环的心脏——它决定了 AI 是作为一个多步执行者还是一个单轮问答者。

## 消息准备

在每一轮循环中，系统需要将累积的对话历史转化为 API 能够理解的格式。这听起来像是一个简单的格式转换问题，但实际上消息准备是整个循环中最容易被低估的复杂性来源——因为历史消息的类型多样、状态繁杂、质量参差不齐，直接送入 API 几乎必然导致问题。

消息类型的丰富程度超出了直觉。内部使用一套强类型的联合类型系统来区分不同种类的消息：用户输入进入 UserMessage，模型响应进入 AssistantMessage，系统边界标记和指令进入 SystemMessage，进度状态进入 ProgressMessage，附件注入（比如 Memory 文件或技能列表）进入 AttachmentMessage，部分响应失效标记进入 TombstoneMessage。这种分类不仅仅是为了类型安全——每种消息类型在后续的规范化和转换流程中有着完全不同的处理规则。

消息规范化流水线是 API 调用前的第一道关卡。它执行一系列剥离、过滤、合并和上浮操作，这些操作各有各的目的。进度消息被剥离，因为它们只包含 UI 渲染信息，对模型没有意义。虚拟消息——比如 REPL 内部的工具调用——被过滤掉，因为它们对应的是界面操作而非实际对话。连续的用户消息被合并为一条，这是为了兼容某些 Provider（如 Bedrock）的限制。已经断开连接的 MCP 服务器的工具引用块被剥离，因为模型不应该看到不可用的选项。曾经导致错误的文档或图片块也被剥离——比如超大的 PDF 或过大的图片，如果模型再次尝试处理它们，几乎必然重复同样的失败。Attachment 消息被上浮以匹配工具结果的位置关系。最关键的一项操作是在调用前删除 `toolUseResult` 的原始负载——这些数据在 UI 渲染完成后就不再需要，保留它们只会让上下文窗口无限膨胀。

格式转换是一个从内部表示到 API 表示的映射过程。内部的 Message 类型结构丰富，包含的元数据远多于 Anthropic SDK 的 MessageParam 所能承载的。转换函数将每条消息映射为 SDK 支持的格式，其中 cache_control 标记被精确定位到每条消息的最后一个内容块上——这是控制 Prompt Cache 命中率的关键细节。Gemini Provider 相关的元数据在此步骤被剥离，thinking 和 redacted_thinking 块的 cache_control 标记被跳过以避免缓存冲突。

工具结果的格式化是消息准备中最具仪式感的一环。每个工具执行结果被包装为一个 `tool_result` 内容块，通过 `tool_use_id` 和 `sourceToolAssistantUUID` 两个标识符精确定位到原始的 `tool_use` 块。这种配对机制确保了在多工具并行执行的场景下，每个结果都能正确地归属于对应的工具调用请求。错误结果被特殊标记为 `is_error: true`，错误内容被包裹在 `<tool_use_error>` 标签中，为模型提供一个清晰的错误信号。

可以这样理解消息准备的全过程：对话历史就像是未经处理的原材料，可能混有杂质（无效消息）、重复（连续用户消息）、过期的调料（已断开的工具引用）和有害物质（过大的附件）。规范化流水线就是一道过滤和提纯的工序，将原材料处理为 API 能够安全消费的纯净输入。

## System Prompt 动态组装

如果消息准备是输入处理的"下游工程"，那么 System Prompt 组装就是输入处理的"上游工程"——它在每一轮循环中构建模型行为的"宪法"，决定模型如何看待自己的角色、可以做什么、不可以做什么。

System Prompt 的构建从三个完全独立的上下文源并行获取信息。第一个源是 `defaultSystemPrompt`，通过 `getSystemPrompt()` 生成，包含固定的角色描述、任务执行指令、工具使用指引和输出效率要求。第二个源是 `userContext`，通过 `getUserContext()` 获取，主要包含项目中的 CLAUDE.md 文件和当前日期信息。第三个源是 `systemContext`，通过 `getSystemContext()` 生成，包含 Git 状态的快照和缓存断点检测用的注入标记。这三个源并行获取而非串行拼接——每一轮迭代中它们同时开始加载，最后合并为一个整体的系统提示。

这种三层并行的结构背后有一个重要的考量：CLAUDE.md 的加载策略。CLAUDE.md 文件不在 System Prompt 内部拼装，而是通过消息前缀的方式注入到对话的起始位置。项目指令内容被包裹在 `<project-instructions>` 标签中，标记为 `isMeta: true`，代表高权重的指令；日期和环境信息则被包裹在 `<system-reminder>` 标签中，标记为低权重——即"可能相关也可能不相关"的背景信息。这种区分使模型能够识别哪些是必须严格遵守的约束（项目指令），哪些是仅供参考的上下文（环境信息）。

System Prompt 内部还有一个重要的结构区分：静态段和动态段。静态段包含角色描述、工具指引等在整个会话中基本不变的内容，这是 Prompt Cache 价值最大的部分。动态段则包含会话引导信息、Memory 内容、模型覆盖信息、MCP 指令等可能随会话进展而变化的内容。两者之间通过一个明确的边界标记 `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 分离。这个边界的意义在于：当动态段的内容变化时，只有边界之后的部分需要重新计算缓存键，边界之前的静态段仍然可以利用已有的缓存——这是一个精心设计的"缓存层次结构"，将缓存失效率控制在最小范围。

动态段的注册通过 `systemPromptSection()` 注册器实现，这是一个插件式的接口：不同的功能模块各自注册自己需要的动态段内容，系统在组装时按确定性顺序将它们合并。这种设计避免了单一函数的臃肿，同时保持了输出顺序的可预测性——这对 Prompt Cache 的稳定性至关重要。值得注意的是，系统还提供了一个 `DANGEROUS_uncachedSystemPromptSection()` 方法，供那些明确知道自己内容不应被缓存的功能使用——命名中的 "DANGEROUS" 前缀是一个刻意的警告信号。

Beta Header 锁存是另一个关乎缓存稳定性的设计。某些动态特性（如 AFK 模式、Fast 模式、Cache 编辑）通过 HTTP Header 传递到 API。如果这些 Header 在会话中途发生变化，会导致整个缓存的失效——大约 50K 到 70K Token 的缓存内容需要重新计算。为了防范这个问题，系统在会话启动时将这些动态 Header 锁存为固定值，在整个会话期间保持不变。这类似于在飞机起飞前锁死飞行模式开关——一旦设定，中途不可更改。

## 流式 API 通信

如果说消息准备和 System Prompt 组装是"把饭做好"，那么 API 通信就是"把饭端上桌"的过程。用户最终感知到的延迟，绝大部分发生在这个阶段。

流式 API 通信的第一道关卡是 Provider 路由。系统支持六个 Provider——Anthropic first-party、OpenAI 兼容层、Gemini 兼容层、Grok 兼容层、AWS Bedrock 和 Google Cloud Vertex。路由决策在共享预处理（消息规范化、工具过滤、媒体剥离）完成之后执行，而非之前。这意味着无论最终使用哪个 Provider，消息都经过相同的规范化管道，保证了行为的一致性。Provider 的选择优先级是：显式的 `modelType` 参数优先，其次是环境变量，最后是默认的 first-party。这种优先级设计使路由策略既支持代码级的精确控制，又支持部署时的灵活配置。

在 Anthropic first-party 路径上，最值得关注的设计决策是原始流优化。官方 SDK 提供 `BetaMessageStream` 封装，它在每个 `input_json_delta` 事件上执行部分 JSON 的解析——累积效果是 O(n) 的额外开销，随着工具调用输入的增长而线性放大。项目选择了直接使用底层 API 的原始事件流（`BetaRawMessageStreamEvent`），手动管理工具输入的累积。这个选择类似于在 JSON 解析器层面手动管理内存分配：收益是性能提升，代价是工程复杂度的增加。

事件处理循环本质上是一个状态机，维护着六种核心事件的处理逻辑。`message_start` 事件触发时，系统捕获 `partialMessage` 的初始状态、首 Token 时间戳（TTFB）和初始 usage 数据——这些是延迟测量和成本追踪的基础数据。`content_block_start` 事件初始化内容块的类型判断——是 tool_use、text 还是 thinking 块。`content_block_delta` 事件是流式传输的核心——文本内容以数组 push 的方式累积（避免字符串拼接的 O(n) 问题），工具调用输入以字符串累积方式拼接。`content_block_stop` 事件将累积的文本 deltas 合并为完整的 AssistantMessage 并产出。`message_delta` 事件更新最终的使用量和终止原因。每个原始事件也同时产出供上层 UI 组件使用——这是流式渲染能够实时更新终端的基础。

流式通信中最容易被忽视的风险是"静默挂起"——API 既不返回错误也不返回新数据，连接看似活着但实际已经死亡。为了防范这种情况，系统实现了一个三层看门狗机制：默认 90 秒的流空闲超时（`STREAM_IDLE_TIMEOUT_MS`）、45 秒的警告计时器（`STREAM_IDLE_WARNING_MS`）和 30 秒的停顿检测阈值（`STALL_THRESHOLD_MS`）。超时后，系统会自动中止当前流并触发非流式回退。

非流式回退是流式通信的最后一道防线。任何流式错误（用户主动中止除外）都会自动触发一次非流式重试。远程会话（CCR）的超时时间为 120 秒——这个值刻意低于远程容器空闲终止的约 5 分钟阈值。本地会话的超时时间为 300 秒。流创建返回 404 时同样触发回退，以处理不支持流式传输的 API 网关。用户可以通过环境变量禁用这个回退行为，但默认是开启的——这是"宁可慢一点也不要失败"的设计原则的体现。

## 工具并发调度

当模型决定调用工具时，循环进入了一个全新的复杂性维度——工具并发调度。如果把 API 通信比作"采购原材料"，那么工具执行就是"加工制造"的过程。制造环节的效率直接决定了整体吞吐量。

工具通过 `Tool<Input, Output, Progress>` 泛型接口注册，这个接口拥有超过 50 个方法，涵盖渲染 Hook（如何展示工具调用和工具结果）、权限 Hook（如何检查和校验输入）和 UX Hook（用户面对的名称和活动描述）。`buildTool()` 工厂函数为所有可选属性提供安全默认值——`isConcurrencySafe` 默认为 false（不并发），`isReadOnly` 默认为 false（可写），`isEnabled` 默认为 true。这种"fail-closed"的设计哲学确保任何未显式声明安全性的工具，默认都被视为不安全。

工具池的组装分多层进行。首先获取全量工具列表（约 50 个以上的工具，通过 feature flag 条件加载），然后按权限拒绝规则过滤，最后将内置工具和 MCP 工具合并排序。排序的确定性至关重要——工具数组的顺序直接影响 System Prompt 的缓存键，任何一次运行中工具顺序的不同都会导致缓存失效。

当工具总数超过阈值时，系统启用延迟工具加载机制。延迟工具的 Schema 被排除在 API 的工具数组之外——这意味着模型在常规的工具数组中看不到它们。模型通过 `SearchExtraToolsTool`（基于 TF-IDF 的语义搜索）发现这些隐藏工具，然后通过 `ExecuteExtraTool` 调用它们。这个设计有两个精妙的副作用：第一，API 请求中的工具 JSON 保持稳定（因为隐藏工具的 Schema 不在其中），有助于 Prompt Cache 的稳定性；第二，工具集可以无限扩展而不增加每次 API 调用的负载。

工具并发执行有两条路径，通过开关控制。在传统的 Batch 模式下，工具调用被分拆为若干批次：每批次要么是一个单独的非并发安全工具，要么是多个连续的并发安全工具。并发批次使用 `Promise.all()` 并行执行（最大并发数 10，可配置），非并发批次则串行执行。这个模式直观且易于理解，但有一个根本性的效率问题——它必须等待所有工具调用结果都从 API 流式到达后才能开始任何执行。

流式模式解决了这个问题。在这种模式下，工具在 API 流式产出 `tool_use` 块的同时就开始执行——不需要等待完整的响应到达。内部队列维护着每个工具的状态转换：queued -> executing -> completed -> yielded。非并发工具充当队列的"屏障"——当模型在非并发工具之后又请求了其他工具时，屏障确保这些后续工具必须等待非并发工具完成后才能开始执行。兄弟错误级联规则进一步精细化了并发控制：Bash 工具执行失败时，同一批次中所有并发的兄弟任务都被中止（因为 Bash 失败通常意味着状态不明确，继续执行其他操作可能产生不可预测的副作用）；相反，Read 或 WebFetch 工具失败时不会级联中止——因为它们只是读取操作，一个读取失败不影响其他读取的可靠性。

## 异常兜底（分层防御）

无论消息准备如何细致、流式通信如何可靠、工具调度如何高效，在真实的网络环境中，失败是不可避免的。异常兜底机制是整个循环的最后屏障。项目实现了一个六层防御体系，每一层解决特定类型的失败，层与层之间通过链式触发关系协作。

第一层是 `withRetry` 重试机制。它实现指数退避算法，以 500 毫秒为基数、二的指数次幂递增，上限 32 秒，引入 25% 的随机抖动避免雪崩效应。重试最多执行 10 次。不同 HTTP 状态码触发不同的处理逻辑：401 触发 OAuth 刷新，403 标记 Token 吊销，429 通知限流订阅者，529 连续三次后触发模型回退。一个值得关注的细节是前台请求和后台请求的区别对待——当服务端返回 529 过载状态时，后台源（摘要生成、标题生成、分类器等辅助请求）立即退出，不进入重试路径。这是因为后台请求的多次重试可能将网关负载放大 3 到 10 倍，在前台已经过载的情况下，后台不应该火上浇油。

第二层是流式回退。任何流式错误（用户主动中止除外）自动触发非流式重试。用户主动中止产生的 `APIUserAbortError` 被特殊处理——直接向上传播而不触发回退，因为中止是用户意图的明确信号，系统不应该自作主张地覆盖。在流式中断时，已经产出的部分 Assistant 消息在 UI 中被标记为 tombstone，防止用户看到不完整的响应。

第三层是模型回退。当 `FallbackTriggeredError` 被抛出时（通常在连续三次 529 后），系统切换到预设的回退模型。所有已累积的 assistant 和 tool 消息被清除，创建全新的执行器。这个"干净重启"的语义很重要——模型切换后，原有上下文中的某些假设可能不再成立，从头开始是最安全的做法。

第四层是恢复重试。这层处理的是流式完成但结果异常的复杂情况。当响应正常返回但没有工具调用时，系统检测几种具体的异常模式并进行不同的处理。Prompt 过长导致模型输出被截留时，系统执行三级递进恢复：先尝试 Collapse drain（丢弃非关键上下文），再尝试 Reactive Compact（主动压缩），最后报错。媒体尺寸错误时跳过 Collapse 阶段——因为 Collapse 无法剥离图片——直接进入 Reactive Compact。输出 Token 达到上限时，系统将上限从 8K 逐步升级到 64K，同时注入"从你停下的地方继续"的续接提示，最多恢复 3 次。这个"自动调整输出上限"的设计非常实用——模型有时确实需要更多的输出空间来完成复杂的推理，而粗暴地截断只会导致无效的输出。

第五层是 Stop Hook。当完整响应没有任何工具调用时——即模型选择直接回答用户——Stop Hook 介入评估。如果评估发现阻塞性错误（比如模型应当调用工具但忘记了），Hook 注入错误消息并继续循环；如果没有问题，循环正常终止。API 错误发生时，Stop Hook 被跳过——这是为了防止"错误-Hook 阻塞-重试-再次错误"的死循环螺旋。

第六层是 Token 预算续接。当当前轮的输出 Token 数低于目标预算时，系统注入续接提示，促使模型继续产出。当收益递减（模型连续多轮产出质量下降）时提前终止，但正常记录完成事件。这个机制确保了 Token 预算被充分利用，同时防止模型在质量下降后仍无意义地消耗资源。

六层防御体系之间通过一组螺旋防止机制保障稳定性。`hasAttemptedReactiveCompact` 单次守卫确保 Reactive Compact 在同一轮中只执行一次。`MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3` 限制了输出 Token 的自动升级次数。API 错误时跳过 Stop Hook 的规则切断了"错误-重试"螺旋的关键链路。Auto-Compact 断路器在连续 3 次失败后停止自动压缩。Reactive Compact 守卫在 Stop Hook 循环间持续保持、不会在循环迭代间重置，防止反复进入压缩-失败-重试的死循环。

## 设计权衡总结

回顾 Agent 核心运行循环的整体设计，可以提炼出几个贯穿始终的设计权衡。

状态管理采用了"可变跨迭代"模式。循环使用 `let state: State` 配合每次迭代顶部的解构，`continue` 站点通过 `state = { ... }` 的方式更新状态（共 9 处独立赋值）。这与不可变快照模式（每次迭代创建全新的状态对象）相比，性能更优（没有深拷贝开销），但可追踪性较差（多个站点修改同一状态）。设计文档明确承认这个选择是为了给未来提取为纯 reducer 模式 `(state, event, config) -> state` 留下空间——这是一个务实的"先让功能跑起来，再考虑形式优雅"的工程决策。

Prompt Cache 保真被提升为一级关注点。这是对"AI 编码工具的核心成本在 API Token 消耗"这一现实的技术回应。工具数组按确定性顺序排序；内置工具形成连续前缀，防止 MCP 工具插入破坏缓存连续性；动态 Beta Header 会话级锁存；延迟工具 Schema 排除在 API 工具数组之外；`systemPromptSection()` 与 `DANGEROUS_uncachedSystemPromptSection()` 的区分设计。这些看起来零散的措施都指向同一个目标：尽可能减少每轮迭代间的缓存失效，将 Token 成本控制到最低。

依赖注入模式在查询核心中被小范围使用。`QueryDeps` 注入四个依赖项——`callModel`、`microcompact`、`autocompact` 和 `uuid`——使测试可以替换为 fake 实现，无需模块导入 spy。这个注入的范围被刻意窄化（仅 4 项），目的是验证模式的可行性而非全面推行。这是一种"够用就好"的工程判断——过度的依赖注入会增加代码的间接性，在大型代码库中反而降低可维护性。

Provider 抽象策略选择了一条中间路线。不使用硬性的抽象层（如定义一个通用的 `ModelProvider` 接口让所有 Provider 实现），而是在共享预处理（消息规范化、工具过滤、媒体剥离）后在 `queryModel()` 中直接分发。每个 Provider 获取规范化的消息和完整工具列表，各自内部处理格式转换。这种设计避免了 Provider 抽象层的接口膨胀和版本漂移问题，但代价是每个 Provider 需要独立实现 Anthropic 兼容的工具使用语义——这是一个"为六种类型各写一遍，但让每种类型都能最优"的权衡。

工具接口设计在丰富与简洁之间找到了平衡。50+ 个方法看似庞大，但 `buildTool()` 为每个方法提供了 fail-closed 的安全默认值，使工具定义本身保持简洁。一个典型的工具定义只需要实现 `inputSchema` 和 `call` 两个核心方法，其余 48+ 个方法在需要时覆盖即可。这种"默认安全、按需定制"的模式既有大型框架的完备性，又有轻量框架的易用性。

内存管理针对长时间运行会话做了专门优化。`toolUseResult` 的原始负载在 UI 渲染完成后被删除，防止渲染数据在上下文窗口中无限累积。原始流资源在流结束后通过 `cleanupStream()` 显式释放。`contentReplacementState` 按消息预算管理聚合工具结果大小。每轮循环结束后清除 JavaScript Core 的性能缓冲区（marks、measures、resource timings）。Langfuse 的 Span 在轮次结束时关闭以允许垃圾回收。这些零散的内存管理措施共同应对一个核心挑战：一个可能运行数小时的会话，如果不在每轮循环中主动清理，内存泄漏几乎是必然的。

## 小结

本章从 Agent 核心运行循环的整体架构出发，逐层解析了支撑这个循环稳定运行的五个子系统。消息准备负责将杂乱的对话历史转化为 API 能够消费的纯净输入，System Prompt 动态组装通过三层并行上下文源和静态/动态段的分离保障了 Prompt Cache 的效率，流式 API 通信通过原始流优化和看门狗机制实现了低延迟高可靠的数据传输，工具并发调度通过 Batch/Streaming 双路径解决了多工具执行的效率问题，异常兜底通过六层防御体系为循环提供了从重试到模型回退的完整容错保障。

贯穿这些子系统的设计哲学可以概括为四句话：让缓存命中成为默认而非例外，让失败恢复自动化而非等待用户介入，让并发效率最大化而不牺牲安全性，让状态管理有明确规则而非随意漫游。这些设计并非来自理论推演，而是来自对 AI 编码工具在实际使用中暴露的每一个痛点的逐一回应——每一个机制背后都有一个真实的失败案例和一个真实的用户投诉。

在下一章中，我们将把目光从"循环本身"转向"循环中的上下文管理"——这是一个更隐蔽但同样关键的问题：当对话累积到数万条消息、数百万 Token 时，如何在不丢失关键信息的前提下将上下文压缩到模型能够处理的范围。
