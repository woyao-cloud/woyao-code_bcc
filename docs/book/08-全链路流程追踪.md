# 第八章：全链路流程追踪

前七章分别介绍了 Claude Code 的各核心子系统。本章以一个真实的用户请求为例，从用户输入到最终输出，完整追踪一次 Agent 循环的全链路。每一步都会标注涉及哪个子系统、产生了什么埋点事件、以及可能触发哪些优化/降级策略。

## 8.1 场景设定

**用户行为**：用户在终端中输入了一条指令，要求 AI 分析项目中的一个 bug 并修复它。

## 8.2 步骤一：输入捕获与预处理

**涉及模块**：REPL Screen / PromptInput / AppState

用户按下 Enter 后：

1. **输入捕获**：PromptInput 组件捕获用户输入的原始文本
2. **命令识别**：系统检查输入是否是 slash command（`/compact`、`/clear` 等）或 shell escape（`!git status`）
3. **消息构建**：普通文本输入被包装为 `UserMessage` 结构
4. **AppState 更新**：新消息被追加到 AppState 的消息列表中
5. **触发 query**：`handlePromptSubmit` 调用 `onBeforeQuery` 回调，然后调用 `query()`

**潜在优化点**：
- 如果在用户打字期间预计算了部分上下文，这一步的"消息构建"会更快
- 如果输入包含文件路径，需要读取文件内容并编码为附件——大文件会有延迟

## 8.3 步骤二：System Prompt 组装

**涉及模块**：context.ts / claudemd.ts / AppState

在发送 API 请求前，系统需要组装完整的 System Prompt：

1. **角色定义**：注入"你是谁"的基础 system prompt
2. **环境信息注入**：
   - 当前时间、时区
   - Git 分支、最近提交、未跟踪文件
   - 操作系统和 Shell 类型
   - 当前目录和项目根目录
3. **CLAUDE.md 加载**：
   - 扫描全局 `~/.claude/CLAUDE.md`
   - 扫描项目根 `CLAUDE.md`
   - 扫描工作目录级 `CLAUDE.md`（如果存在）
   - 三级内容拼接后注入 System Prompt
4. **Memory 注入**：
   - 读取 `~/.claude/memories/` 中与当前项目相关的记忆
   - 格式化为"关于此用户的已知信息"段落
5. **工具列表构建**：
   - 合并内置工具 + MCP 工具 + 自定义 agent
   - 根据 feature flag 启用/禁用
   - 格式化为 JSON Schema 用于工具定义
6. **系统指令注入**：
   - settings.json 中的 `systemPrompt` / `appendSystemPrompt`
   - policy 强制指令
   - Hook 返回的注入内容

**埋点**：`logAPIQuery` 被调用，记录 model、permissionMode、querySource 等信息。

## 8.4 步骤三：API 请求与流式响应

**涉及模块**：query.ts / services/api/claude.ts / Stream 类

1. **请求构建**：
   - 选择模型（firstParty/Bedrock/Vertex/OpenAI/Gemini/Grok）
   - 组装请求参数：model、messages、tools、thinking_config、betas
   - 构建缓存前缀
   - 创建 AbortController（用于取消）

2. **请求发送**：
   - 通过 Anthropic SDK 发送 streaming request
   - 记录 `previous_request_id`（用于缓存关联）
   - 检查是否触发 cache hit（影响首 token 延迟）

3. **流式响应处理**：
   - `message_start` → 记录 message ID
   - `content_block_start` → 准备新的 content block
   - `content_block_delta` → 逐 token 解析，通过 Stream.enqueue() 推送到渲染层
   - `message_delta` → 更新 token usage、检查 stop_reason
   - `message_stop` → 标记流结束

**潜在异常**：
- 529 过载 → 指数退避重试
- 网络超时 → 自动重试 1 次
- Stream 提前中断 → 重试或降级

**埋点**：`logAPIQuery` 记录首 token 到达时间、总延迟。

## 8.5 步骤四：工具调度与执行

**涉及模块**：useStreamingToolExecution / Tool 注册表 / permissions 层

当模型的 stop_reason 为 `tool_use` 时：

1. **解析工具调用**：
   - 从 API 响应中提取所有 content block 中 type 为 `tool_use` 的块
   - 每个块包含 toolName、input（JSON）、id

2. **查找工具定义**：
   - 在工具注册表中按 name 查找对应的 Tool 对象
   - 如果未找到（如 MCP 工具断开），生成"工具不存在"的 error result

3. **权限检查**：
   - 调用 `tool.canUse()` 进行权限检查
   - 根据 permission mode（allow/deny/ask）决定是否放行
   - 如果是 "ask" 模式，弹出交互式权限确认窗口

4. **并发执行**：
   - 所有工具调用同时启动（不串行等待）
   - 每个工具有自己的执行上下文（ToolUseContext）
   - 每个工具在自己的异步任务中运行

5. **结果收集**：
   - 等待所有工具调用完成
   - 使用 `ensureToolResultPairing` 确保每个 tool_use 都有对应的 tool_result
   - 如果某个工具有空结果，生成兜底 tool_result

6. **Attribution 记录**：
   - 记录每个工具的 token 消耗、执行时间
   - 更新 AttributedCounter
   - 如果是子 Agent，调用 `logForkAgentQueryEvent`

**本例中的典型工具调用**：
- `Grep`：搜索关键词 → 找到相关代码行
- `Read`：读取文件内容 → 获取完整源码
- `Glob`：搜索相关文件 → 发现影响范围
- `Agent`：委派子 Agent 分析复杂逻辑（可选）

**降级场景**：
- 文件不存在 → 返回空结果，AI 自动调整路径
- 命令超时 → 返回部分结果，AI 决定是否继续
- 权限拒绝 → 返回错误，AI 提示用户授权

## 8.6 步骤五：结果回送与第二轮 API 调用

**涉及模块**：query.ts / Agent Loop

工具结果收集完毕后：

1. **构建结果消息**：将 tool_result 列表包装为 UserMessage（role: "user"）
2. **追加到消息列表**：新消息追加到消息流中（顺序：...assistant_msg → tool_result）
3. **再次调用 API**：携带扩增后的消息列表重新请求

此时触发**第二轮 Agent 循环**：
- 模型看到工具返回的结果
- 如果信息不足，可能继续调用更多工具
- 如果有足够信息，开始生成修复代码

**持续循环**：
```
Round 1: "分析 bug" → Grep/Read → 找到相关代码
Round 2: "需要更多上下文" → Glob/Read → 了解影响范围
Round 3: "开始修复" → FileEdit → 修改代码
Round 4: "验证修复" → Bash(run test) → 测试通过
Round 5: "end_turn" → 向用户展示完成结果
```

**轮次控制**：
- 没有硬性轮次上限——模型自行决定何时 "end_turn"
- Token budget 用尽时自动触发 compaction
- 用户可随时 Ctrl+C 中断

## 8.7 步骤六：Compaction（如果触发）

**涉及模块**：compactConversation / autoCompact

如果本轮对话的消息数接近阈值，在下一轮 API 调用前自动触发 Compaction：

1. **Pre-Compact Hooks**：
   - 执行用户配置的 pre_compact hooks
   - 收集自定义指令（"保留关于认证模块的上下文"）
   - 展示 "正在压缩..." 状态给用户

2. **LLM 压缩**：
   - 将早期消息发送给 Haiku 模型
   - 生成结构化摘要：已经完成的步骤、文件修改、关键决策
   - 摘要格式化为新的 UserMessage

3. **边界标记**：
   - 在消息列表中插入 `CompactBoundaryMessage`
   - 对用户显示一条线："之前的对话已压缩"
   - 用户仍然可以感知到"上下文被整理了"

4. **Post-Compact Cleanup**：
   - 更新 token 计数
   - 清理缓存状态
   - 记录 compaction 的 token 消耗

**埋点**：Compaction 事件会被记录（pre/post token count、usage）。

## 8.8 步骤七：最终输出与后处理

**涉及模块**：REPL / stream 渲染 / extractMemories

1. **流式渲染**：
   - 最终模型的文本输出通过 Stream class 逐 token 推送
   - Ink 使用 damage region diff 逐帧渲染
   - 用户看到完整的修复方案

2. **会话结束**：
   - 模型返回 `stop_reason: "end_turn"`
   - 最后一个 assistant message 记录完毕
   - Agent 循环结束

3. **用户交互**：
   - 用户看到 AI 的回答和变更
   - 用户可以进行 follow-up（"解释一下这个修复"）
   - 或者结束会话

4. **会后处理**（后台）：
   - `extractMemories`：分析对话，提取用户偏好和项目约定
   - 如果启用了 verification_agent：验证代码变更的质量
   - 写入 Memory 文件（持久化）
   - Hook cleanup 执行

## 8.9 全链路埋点总览

以上整个过程产生的事件链：

```
logAPIQuery (步骤三：API 调用 #1)
  └─ logAPIQuery (步骤三：API 调用 #2 - 第二轮)
  └─ logAPIQuery (步骤三：API 调用 #3 - 第三轮)
  └─ ...
  └─ logForkAgentQueryEvent (如果有子 Agent)
  └─ Compaction 事件 (如果有触发)
```

## 8.10 典型场景的路径分析

| 场景 | 路径 | 关键延迟 |
|------|------|----------|
| 简单问答 | Enter → 一步 API → 文本输出 | 模型推理时间 |
| 代码搜索 | Enter → API → Grep/Read → API → 文本 | 工具执行时间 |
| 代码修改 | Enter → API → Read/Glob/Grep → API → FileEdit → API → Bash(test) → API → 完成 | 多轮 API + 工具执行 |
| 多 Agent 协作 | Enter → API → AgentTool(子 Agent) → (子 Agent 的多轮循环) → API → 汇总 | 子 Agent 的执行时间 |
| 长对话恢复 | ... → Compact → API → 继续 | Compaction 时间 |
| 工具失败 | Enter → API → 工具超时 → 降级结果 → API → 重试 → API → 完成 | 额外重试时间 |

## 8.11 架构总结

回到第一章的六层架构图，现在我们可以标注每一层在此流程中的贡献：

| 层次 | 在流程中的角色 |
|------|---------------|
| **入口层** | 决定走哪种模式（CLI / daemon / bridge） |
| **引导层** | 加载配置、初始化状态、连接 MCP |
| **核心循环层** | 编排整个 Agent 循环（步骤二至六） |
| **API 层** | 流式通信、重试、缓存 |
| **工具系统** | 提供 60+ 工具的能力（步骤四） |
| **UI 层** | 渲染输出、权限交互、状态反馈 |

每个层次都不是单独存在的——它们在用户的一次 Enter 按键中协同工作，在毫秒级内完成从感知到行动的完整循环。

---

**结语**：Claude Code CLI 是一个深度工程化的 AI Agent 系统。它的架构不是"把大模型包装到终端里"，而是在终端、模型、工具和用户之间建立了精心设计的交互协议。每一层都有自己的约束和优化目标，每一层都与其他层有明确的接口边界。理解这些设计，不仅能帮助你更好地使用这个工具，也能为你构建自己的 Agent 系统提供参考。
