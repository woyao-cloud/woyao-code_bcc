# 第六章：C 端体验关键指标优化

在终端环境中使用 AI Agent，用户的耐心窗口极短——500 毫秒的延迟就足以让思维"断片"，一次静默失败就足以让信任受损。本章深入 Claude Code 在首 token 延迟、流式输出、降级策略和静默失败检测四个关键指标上的优化策略。

## 6.1 首 Token 延迟（TTFT）

从用户按下 Enter 到第一个 token 在屏幕上出现的时间，是决定用户体验的**最关键指标**。

### 延迟拆解

一个典型的"Enter → 首 token"旅程包含以下阶段：

```
[用户 Enter]
    ↓ 0-50ms: 输入捕获 & 消息构建
        ↓ 0-30ms: System Prompt 组装
            ↓ 0-500ms: 消息预处理（附件编码、工具列表构建）
                ↓ 网络: API 请求传输
                    ↓ 服务端: 模型推理（主要延迟源）
                        ↓ 网络: 首个 token 返回
                            ↓ 0-16ms: Ink 渲染帧
[用户看到第一个字]
```

主要延迟源（按影响排序）：

1. **模型推理时间**（80%+）—— 不可控的 API 端延迟
2. **预处理时间**（10%）—— System Prompt 组装、消息构建
3. **网络传输**（5-10%）—— 取决于用户地理位置
4. **渲染时间**（<5%）—— Ink 的 diff 渲染

### 优化策略

**（1）预处理并行化**

消息构建和 System Prompt 组装不是完全串行的。在系统等待用户输入时，部分上下文可以"预计算"：
- CLAUDE.md 文件的扫描和缓存
- 项目结构的预检测
- Memory 文件的预读取

这些计算的结果缓存一段时间，用户输入到达时直接使用，减少等待时间。

**（2）API 请求前置**

当用户输入被识别为"明确的编程任务"时，系统可以在用户输入完整前就开始部分初始化（如建立 TCP 连接、发送 HTTP headers）。

**（3）缓存优先**

Prompt Cache 对 TTFT 的影响显著——cache hit 时服务的响应速度远快于 cold start。优化策略包括：
- 保持缓存前缀的稳定性（减少变更导致 cache break）
- 尽量在前缀中放置不变的 System Prompt 内容
- 监控 cache hit rate，低于阈值时告警

**（4）渲染层优化**

消息到达后，渲染层使用增量 diff 而非全量重绘。Ink 的 `damage` 机制只更新变化区域的 cell，减少渲染开销。

### 监控指标

系统通过以下指标监控 TTFT：
- `api_duration`：API 请求到首 token 返回的时间
- `total_api_duration_without_retries`：排除重试的净耗时
- `build_age_minutes`：构建时间（新构建的优化可能不同）

## 6.2 流式输出流畅度

首 token 到达后，后续内容的输出流畅度同样重要——"卡顿"比"慢"更让用户烦躁。

### 流畅度的挑战

终端中的流畅度与浏览器环境不同：
- **帧率**：终端没有 60fps 的概念，但用户能感知到"一顿一顿"的输出
- **渲染开销**：每次内容更新都需要 Ink 执行完整的 diff + 刷屏操作
- **字符集**：Unicode 字符（中文、emoji）的处理比 ASCII 复杂

### 优化策略

**（1）Virtual Scroll**

在长对话中，消息列表可能包含数百轮对话。如果每帧都渲染全部消息，性能会急剧下降。

Virtual Scroll 机制只渲染可见区域的消息（约 40 行），上下滚动时动态替换渲染内容。这使得即使在数百条消息的对话中，渲染性能也保持恒定。

**（2）Damage Region 优化**

Ink 的 diff 机制不比较整个屏幕，只比较有变化的区域（damage region）。流式输出时，只有新到达的 token 区域被标记为 damage，渲染器只更新这些区域。这减少了大量的 cell 比较开销。

**（3）批量刷新**

不是每个 token 到达就立即刷新屏幕。Ink 使用 requestAnimationFrame 风格的批处理——在单个渲染帧内累积所有变化，然后一次性输出。这避免了"闪烁"（每个 token 刷新一次导致屏幕抖动）。

**（4）思考模式（Thinking Indicator）**

当模型处于"思考"状态（extended thinking），终端不会静默等待——系统会展示：
- 实时的思考内容流
- 思考进度条（如果模型提供 budget tokens 信息）
- "思考中..."的动画指示器

用户即使看不到最终输出，也能感知到"系统在工作"。

### 极端情形处理

- **输出堵塞**：当模型输出大量内容时，Stream 队列可能堆积。系统会监控 queue 长度，在接近阈值时降速渲染。
- **终端窗口调整**：用户调整窗口大小时，Ink 重新计算几何，调整渲染。流式输出短暂暂停，然后在新的布局中继续。

## 6.3 工具失败的降级策略

工具调用是 Agent 系统中出错概率最高的环节——文件不存在、网络超时、权限不足、Shell 命令异常。降级策略决定了用户在失败时的体验。

### 降级层次

```
第一层：透明重试
  工具超时或临时故障 → 自动重试 1-2 次
  适用场景：网络抖动、文件锁争用

第二层：优雅兜底
  工具执行失败 → 构建合理的 tool_result
  适用场景：文件不存在、命令返回非零
  → 模型看到结果后自主调整策略

第三层：显式错误
  工具无法执行 → 返回错误 tool_result
  适用场景：权限不足、无效参数
  → 模型知道"某个东西出错了"

第四层：中断
  严重异常 → 终止当前 Agent 循环
  适用场景：配置损坏、认证失败
  → 需要用户干预
```

### 具体场景的降级

**文件操作**

- 读文件不存在：返回 `FileNotFoundError`，AI 自动尝试其他路径
- 写文件被拒绝（权限）：返回错误，AI 尝试其他位置或提示用户
- 写大文件超限：截断后写入，返回"已截断"消息

**Shell 命令**

- 命令返回非零：返回 stdout + stderr + exit code，AI 自行判断是否错误
- 命令超时：返回"已超时"和部分输出，AI 决定是否 kill 或重试
- 命令危险（rm -rf /）：被权限层拦截，返回"命令被管理员阻止"

**网络/Git**

- Git 冲突：返回冲突详情，AI 尝试自动合并或建议手动解决
- 网络请求失败：自动重试 1 次，仍失败则返回错误消息

### 空结果处理

最棘手的情况：工具执行返回空结果（没有内容、没有错误、没有输出）。这可能是"真的没输出"也可能是"静默失败了"。

处理策略：
1. 构建一个"无结果"的 tool_result，包含 `isError: false`
2. 在 tool_result 中添加说明："该工具没有返回任何内容"
3. 让模型自行决定是重试还是继续

在 strict 模式下，空结果会触发断言失败——系统宁愿让对话中断，也不让模型在"虚假的空结果"基础上继续推理。

## 6.4 静默失败的检测与兜底

静默失败是最有害的错误模式——没有错误消息、没有异常、但结果是不正确的。在 Agent 系统中，这通常表现为"工具看似执行成功但实际没有效果"。

### 静默失败的类型

1. **文件写入未持久化**：FileWrite 返回成功但文件未更新
2. **命令执行无输出**：Bash 返回空 stdout 但命令实际上失败了
3. **工具注册丢失**：工具被注册但执行时找不到处理函数
4. **Stream 中断**：API 流提前结束但没有错误事件
5. **结果不配对**：工具调用 ID 与结果 ID 不匹配

### 检测机制

**（1）Tool Result Pairing**

`ensureToolResultPairing` 是静默失败检测的第一道防线。它强制每个 `tool_use` 必须有对应的 `tool_result`：

- 遍历所有工具调用，对每个 ID 查找对应的结果
- 如果缺少结果，生成一个"兜底"的 tool_result
- 如果结果数量不匹配（多了一个），记录告警但继续执行

在 strict mode 下，不配对直接抛出错误——宁可挂起也不让系统在"虚假的"结果上工作。

**（2）Stream完整性检查**

流式 API 的结束信号必须检查。系统会验证：
- `message_stop` 事件是否到达（正常结束标志）
- `message_delta` 中的 stop_reason 是否合理
- 内容块的数量是否匹配

如果流提前结束（网络中断、服务端错误），系统会抛出"流中断"错误并触发重试。

**（3）执行超时监控**

每个工具的执行都有超时限制。超过限制后：
1. 记录"工具执行超时"告警
2. 尝试 abort 工具（如果有 AbortController）
3. 生成"工具执行超时"tool_result
4. 继续 Agent 循环（不中断整体流程）

**（4）输出验证**

对于关键操作（文件修改、代码提交），系统会执行后置验证：
- 文件修改后验证文件确实已被更新
- Git 提交后验证提交是否成功

### 兜底策略

当检测到静默失败后：

1. **告知模型**：在 tool_result 中明确告知"此工具返回了空结果"
2. **提供选项**：让模型选择重试、使用替代方法、或继续
3. **记录日志**：记录完整的失败上下文（工具名、输入、预期输出）
4. **用户提示**：在某些场景下提示用户确认

## 6.5 错误恢复

当系统确实出错时（API 崩溃、网络中断、进程崩溃），恢复策略决定了用户的"后怕"程度。

**API 层恢复**

- 529 服务过载 → 指数退避重试（最大 3 次）
- 网络超时 → 立即重试 1 次
- 认证过期 → 提示用户重新登录
- 无效请求 → 不重试（参数错误重试无意义）

**对话层恢复**

当 API 调用恢复时：
1. 重新发送失败时的消息（包括已执行的工具结果）
2. 如果上一步的工具结果在恢复前已过期，让模型重新执行
3. 在消息中插入一条"恢复标记"，说明刚才经历了网络中断

**进程层恢复**

如果进程本身崩溃了（如 OOM）：
1. 会话状态被持久化到本地存储
2. 用户重启后，系统检查是否有"未完成的会话"
3. 提示用户是否恢复
4. 恢复时加载之前的状态，继续对话

## 6.6 响应式反馈设计

除了被动的降级和恢复，主动的反馈机制也显著影响用户体验：

**请求中状态**

当系统正在处理请求时，终端显示：
- `requesting` 动画（旋转的等待指示器）
- 进度条（如果可预估）
- 模型名称（让用户知道正在使用哪个模型）

**思考指示**

当模型使用 extended thinking 时，用户能看到：
- 实时的思考流
- 思考长度指示器
- 剩余 budget tokens

**权限提示**

工具权限提示的交互设计遵循"最小打扰"原则：
- 默认行为（记住我的选择）减少重复提示
- 允许用户设置白名单
- 提示信息简洁，不打断工作流

## 6.7 设计权衡讨论

**（1）自动重试 vs 立即失败**

自动重试提高成功率（网络抖动是临时问题），但增加了延迟。如果重试最终也失败，用户等待了 2× 的时间。

方案：对"有成功可能"的错误（529、timeout）自动重试；对"确定失败"的错误（400、auth fail）立即失败。重试次数限制在 1-2 次，避免无限等待。

**（2）空结果 vs 严格模式**

空结果模式更健壮（Agent 循环可以继续），但可能掩盖真正的错误。严格模式更安全（问题立即暴露），但不适合生产环境。

方案：默认空结果模式，提供 strict 开关（由 `strictToolResultPairing` 控制）。生产环境用常规模式，调试/评测启用 strict 模式。

**（3）渲染性能 vs 功能丰富**

Virtual scroll 提高渲染性能，但限制了用户一次性看到的内容量。完整的消息渲染提供更好的阅读体验，但滚动更慢。

方案：Virtual scroll 默认开启，`CLAUDE_CODE_DISABLE_VIRTUAL_SCROLL` 环境变量可关闭。

---

**本章小结**：C 端体验优化是贯穿 Agent 系统所有层面的系统性工程。从首 token 延迟的毫秒级优化，到工具失败的层次化降级，再到静默失败的检测兜底，每个环节都定义了"最低可接受体验"的标准。下一章将探讨多 Agent 协作架构——当任务复杂到需要多个 Agent 协同完成时，系统如何组织和协调。
