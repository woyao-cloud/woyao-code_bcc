# 第 2 章：Agent 核心运行循环

## 2.1 概述

Agent 核心运行循环是 Claude Code 最核心的机制。它实现了一个"感知-思考-行动"的循环过程：系统将用户输入和上下文组装成 API 请求，发送给 LLM，LLM 返回文本或工具调用请求，系统执行工具并将结果返回给 LLM，如此往复，直到任务完成或达到终止条件。

本章将从以下角度展开：
- 消息构建与准备
- System Prompt 的动态组装
- 流式 API 通信机制
- 工具并发调度与执行
- 结果收集与异常兜底
- 核心模块之间的设计权衡

## 2.2 两个关键类：Query 与 QueryEngine

Agent 循环的实现围绕两个核心模块：

**Query** 是底层的 API 通信函数。它负责将消息列表发送到 Anthropic API，处理流式响应事件，解析工具调用请求。它关注的是"单次 API 调用"的生命周期。

**QueryEngine** 是高层编排器，它封装了整个对话的生命周期。它管理消息列表、Token 使用统计、上下文折叠、文件历史快照、引用追踪等跨轮次的状态。它包含 `submitMessage` 方法，这是一个异步生成器（AsyncGenerator），每次模型返回一个完整响应就 `yield` 一次，上层可以逐次渲染到 UI。

两者之间的关系是：QueryEngine 在每一轮调用 Query，传递精心构建的消息列表和参数；Query 负责流式通信和原始事件解析；QueryEngine 在 Query 返回后处理工具执行和下一轮准备。

## 2.3 消息构建与准备

在每一轮交互中，消息构建经历了以下步骤：

### 消息来源
发送给 API 的消息列表由以下部分组成：
- **对话历史**：之前所有轮次的用户消息和助手消息，可能经过折叠压缩
- **当前用户输入**：新的一轮中用户输入的文本或附加文件
- **系统消息**：插入在对话中的状态更新消息（如工具执行结果、Agent 加入/退出通知）
- **上下文注入消息**：由 ProcessUserInput 钩子在消息发送前注入的额外内容

### 消息投影（Message Projection）
在消息发送给 API 之前，会经过"投影"步骤。ProjectMessagesForAPI 函数负责：
1. 根据 API 要求格式化消息（移除内部字段、调整角色交替）
2. 添加缓存标记（Cache Control）以利用 Prompt Cache
3. 对消息进行轻量级压缩（Microcompact）：删除过旧的工具执行结果，保留最近的
4. 确保消息数组符合 Anthropic API 的规范（以 user 消息开头、角色交替等）

### 消息身份验证
为了优化性能，系统会计算消息列表的"身份指纹"（Message Identity）。这是一个轻量级的哈希，基于第一条和最后一条消息的内容以及消息数量。在连续轮次中如果消息未发生变化，可以直接复用上一次的压缩结果，跳过重复计算。

## 2.4 System Prompt 动态组装

System Prompt 是 Agent 行为引导的最关键因素。它采用**分节（Section）组装**的模式构建：

### 分节注册
System Prompt 由多个命名的"节"组成，每节有一个计算函数（ComputeFn）和一个缓存标记。例如：
- 日期/时间节
- 工作目录信息节
- Git 状态节
- CLAUDE.md 内容节（项目级指令）
- 技能描述节
- 记忆文件内容节
- Agent 定义节
- 环境信息节
- 工具使用指南节

### 缓存感知组装
不是所有节都需要每次都重新计算。系统通过 `systemPromptSection` 和 `DANGEROUS_uncachedSystemPromptSection` 两种注册方式区分：
- **稳定节**（cacheBreak=false）：内容几乎不变，可以重用缓存
- **易变节**（cacheBreak=true）：内容可能经常变化，会触发缓存重建

组装时，系统会将所有节按顺序拼合，并在每个节前后添加缓存控制标记。为了最大化缓存命中率，**前半部分的稳定节**会被标记为 `ephemeral: false`，使其缓存在服务器端持久化；后半部分的易变节会被标记为 `ephemeral: true`，确保更新能及时反映。

### 系统上下文缓存
System Prompt 的构建结果会被缓存（SystemContextState），并在每次轮次开始时失效。当有外部依赖变化时（如 CLAUDE.md 被修改、记忆文件被更新），系统会显式地使缓存失效，确保下一轮使用最新内容。

## 2.5 流式 API 通信

### 通信协议
项目使用 Anthropic Messages API 的流式传输（Streaming），通过 SSE（Server-Sent Events）接收模型输出。主要事件类型包括：
- `message_start`：消息开始，包含消息 ID 和初始使用量信息
- `content_block_start`：内容块开始（文本块或工具调用块）
- `content_block_delta`：内容增量（文本片段的追加或工具调用 JSON 的增量）
- `content_block_stop`：内容块结束
- `message_delta`：消息增量，包含停止原因和累积使用量
- `message_stop`：消息结束

### 流适配器模式（Multi-API 兼容）
对于非 Anthropic 的 Provider（OpenAI、Gemini、Grok），每种都实现了一个流适配器，将各自的流式格式转换为 Anthropic 的事件格式。这样，上层的 Query 函数完全不感知后端是哪个 Provider。例如：
- OpenAI 适配器：将 Chat Completions 流中的 `delta` 事件映射为 Anthropic 的 `content_block_delta`
- Gemini 适配器：将 GenerateContentResponse 流转换为对应的事件序列

### Stream 工具类
项目实现了一个通用的 `Stream` 类，它是一个可异步迭代的队列。上游生产者调用 `enqueue` 添加数据，调用 `done` 结束流；下游消费者通过 `for await...of` 消费数据。这个类在底层 SDK 和上层处理逻辑之间起到了缓冲和适配作用。

### 重试与退避
API 通信层内置了完整的重试机制。RetryService 模块将错误分为七类：
- **rate_limit**（429）：可重试，使用指数退避 + Retry-After 头
- **server_error**（5xx）：可重试，1 秒基础延迟，最大 16 秒
- **connection_error**（超时/网络错误）：可重试，500ms 基础延迟，最大 8 秒
- **auth_error**（401/403）：不可重试
- **prompt_too_long**：不可重试
- **aborted**（用户取消）：不可重试
- **unknown**：尝试重试但保守

对于不可重试的错误，系统会迅速向上层报告错误状态，触发降级策略。

## 2.6 工具并发调度

当 LLM 返回的工具调用到达时，系统使用 StreamingToolExecutor 来管理它们的并发执行。

### 工具执行队列

StreamingToolExecutor 维护了一个工具队列，每个工具进入队列时有三种状态：queued、executing、completed。工具调度的核心逻辑如下：

1. **入队**：当 API 返回一个 tool_use 块时，立即创建一个 TrackedTool 对象并加入队列
2. **权限检查**：每个工具在执行前需要经过 canUseTool 函数的权限检查，根据权限模式决定是否允许执行
3. **并发执行**：系统支持并发执行多个工具。并发规则如下：
   - 如果一个工具声明为"并发安全"（isConcurrencySafe），它可以与其他并发安全的工具同时执行
   - 如果当前没有任何工具在执行，可以启动第一个工具
   - 如果当前有工具在执行，新工具必须也是并发安全的才能启动
4. **顺序保证**：非并发安全的工具会阻塞后面的工具，直到它执行完毕

### 工具中断与降级

当 API 流式传输过程中发生错误需要重试时，系统提供了 `discard` 方法：
- 立即中止所有正在执行的工具子进程
- 清空工具队列
- 释放内部引用以便垃圾回收
- 所有未完成和排队中的工具收到合成错误消息

这种设计避免了"流式回退"时的内存泄漏问题——如果不清理，反复的 API 重试会累积大量的 TrackedTool 对象。

### 工具进度报告

工具在执行过程中可以产生"进度事件"（pendingProgress），这些事件会被缓存并在适当的时机推送到 UI。例如 Bash 工具执行一个长时间命令时，可以将中间输出作为进度事件推送给用户。

## 2.7 结果收集与异常兜底

### 正常流程

一轮 Agent 循环的正常流程是：
1. API 返回流式事件 → 系统收集文本块和工具调用块
2. 所有工具调用执行完毕后，系统将工具结果组装为 user 消息
3. 将工具的 assistant 消息和 tool_result 的 user 消息追加到对话历史
4. 判断是否需进入下一轮：如果有工具调用且有结果，继续；否则结束
5. 每轮结束后检查 Token 使用量，接近预算时提前终止

### 异常兜底策略

系统处理以下异常场景：

**API 流式错误**：如果 API 在流式传输中途失败（网络中断、服务端错误），根据错误类型决定是否重试。若重试也失败，则向上层报告错误。如果是流式回退场景，会丢弃当前所有工具执行结果并重新发送简化后的请求。

**工具执行超时**：每个工具有隐式的执行超时机制。长时间运行的工具（如 Bash 命令）可以通过进度事件通知用户状态。

**工具不存在或输入验证失败**：如果 LLM 调用了不存在的工具，系统会生成一个 `<tool_use_error>` 错误消息返回给模型，而非崩溃。如果工具输入验证失败（JSON Schema 校验），同样返回错误。

**权限拒绝**：如果用户拒绝了工具权限，系统返回 "User rejected tool use" 消息。LLM 可以据此调整行为（例如改用其他工具）。

**预算超限**：系统在每轮结束后检查 Token 使用量和美元预算。如果超过预算限制，会抛出预算超限异常并终止循环。

### 多 Provider 的容错差异

不同 Provider 对 API 响应格式的兼容性不同。OpenAI 兼容层和 Grok 兼容层通过自定义模型映射和响应转换来处理差异。例如 DeepSeek 在 OpenAI 兼容模式下有特殊的 thinking mode 支持。

## 2.8 设计权衡分析

### Agent 循环 vs. 工具注册

**问题**：Agent 循环的灵活性和工具系统的结构化之间存在张力——循环越灵活，工具注册越复杂。

**权衡方案**：项目采用"注册式"工具架构，工具通过标准接口注册（Tool 接口 + inputSchema 校验 + isConcurrencySafe 声明），循环层只关心调度和执行，不关心工具的具体实现。这保持了循环的简单性，同时允许工具系统通过 60+ 工具不断扩展。

### 上下文管理 vs. Agent 循环

**问题**：Context 窗口有限，但对话可能持续数小时。

**权衡方案**：Agent 循环将上下文压缩委托给独立的 Context 管理子系统，循环本身只关心"当前轮次的消息"。压缩在每轮结束时异步进行，不阻塞用户的下一轮输入。这种解耦使得两者可以独立演进。

### 流式体验 vs. 错误恢复

**问题**：流式输出要求低延迟，但错误重试需要重新发送上下文。

**权衡方案**：默认优先保证流式体验，出现错误时先尝试快速重试（NO_FLICKER 模式）。只有重试连续失败时才升级到更保守的策略。此外使用 Prompt Cache 优化重试速度——缓存的前缀内容不会被重复计算，只有增量部分需要重传。

### 单 Agent 循环 vs. 多 Agent 协作

**问题**：主循环是单线程的，但多 Agent 协作需要并行执行。

**权衡方案**：主循环保持单线程的简单性。多 Agent 协作通过 AgentTool 实现——模型在主循环中调用 AgentTool 来启动一个子 Agent，子 Agent 独立运行在自己的循环中，完成后将结果返回主循环。这是一种"嵌套循环"模式，而非"多线程循环"模式。
