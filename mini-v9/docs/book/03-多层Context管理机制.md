# 第 3 章：多层 Context 管理机制

## 3.1 问题的本质

LLM 有一个固定的 Context 窗口（如 200K tokens），而 AI 编程助手的对话可能持续数小时、数百轮。如何在有限的 Context 窗口中保持对话的连贯性和 Agent 的有效性，是 C 端产品面临的核心挑战。

Context 管理需要回答以下几个问题：
- 当对话历史超出 Context 窗口时，怎么压缩？
- 如何确保最重要的信息不被丢弃？
- 如何利用 Prompt Cache 加速重复加载？
- 如何在多 Agent 场景下传递和隔离上下文？

## 3.2 三层 Context 结构

项目的 Context 体系分为三个层次：

### 第一层：System Prompt（系统指令层）
这是最高优先级的上下文，包含 Agent 的行为规则、工具定义、项目级指令等。System Prompt 采用"分节组装"模式，每节可以独立计算和缓存。关键特性：
- **缓存感知**：前半部分（工具定义等稳定内容）启用持久缓存，后半部分（当前目录、Git 状态等易变内容）使用临时缓存
- **分节独立失效**：当某节依赖发生变化（如 CLAUDE.md 被编辑），仅该节需要重新计算
- **Token 预算控制**：System Prompt 总长度受模型窗口限制，超出时按优先级裁剪可选节

### 第二层：对话历史（Messages Layer）
这是用户和 Agent 之间的完整对话记录。管理策略包括：
- **完整保留最近轮次**：最近 N 轮交互保持完整，不做任何裁剪
- **选择性折叠旧轮次**：更早的历史被折叠压缩
- **工具结果压缩**：大型工具执行结果（如文件读取、代码搜索）被优先裁剪

### 第三层：外部上下文（External Context Layer）
包括 CLAUDE.md 文件、Memory 文件、技能描述等外部来源的上下文。这些内容通过 System Prompt 的各节注入到对话中，有独立的 Token 预算和优先级排序。

## 3.3 上下文压缩机制

### 触发时机

上下文压缩在每一轮对话结束时评估是否需要执行。评估基于以下条件：
- **消息数量阈值**：当消息数量超过预设阈值（如 50 条）时触发
- **Token 预算阈值**：当估算 Token 使用量接近模型窗口上限时触发
- **显式请求**：用户可以通过命令手动触发压缩

### 微观压缩（Microcompact）

这是最常用、最轻量的压缩策略。它的核心思想是：**删除旧的工具执行结果，保留最近的结果**。

具体规则：
1. 确定触发阈值（如最近 10 个工具结果）和保留数量（如最近 5 个）
2. 删除超出阈值的旧工具结果，但保留工具调用块本身
3. 在删除位置插入一个 "compact boundary" 标记，在 UI 中显示为折叠提示

这种策略的巧妙之处在于：工具调用块（描述了 LLM 曾经做了什么）仍然保留在上下文中，让模型"知道"自己的历史操作，只是删除了冗长的结果内容（如读取的文件内容）。这被称为"知道做了、但不需要看到结果"的压缩策略。

### 摘要压缩（Summary Compaction）

当微观压缩不足以控制 Context 大小时，系统会触发更激进的摘要压缩：
1. 将早期对话发送给 LLM 进行摘要
2. 用摘要替换原始对话内容
3. 插入 "compact boundary" 系统消息标记压缩边界

摘要压缩通过 ForkedAgent 在后台异步执行，不影响用户的主交互流程。

### Cache-Edits 压缩（高级特性）

对于支持 cache_edits 的模型（Claude 4.x），项目实现了更高效的压缩方式：**不删除内容，而是通过 cache_edits API 标记哪些工具结果应该被缓存忽略**。这种方式避免了物理删除消息导致的缓存失效，保持了 Prompt Cache 的连续性。

Cache-Edits 系统维护一个 CachedMCState，跟踪：
- 已注册的工具结果 ID
- 工具顺序
- 已删除的引用（标记为不可见）
- 固定的编辑块（pinnedEdits）

当工具结果数量超过阈值时，系统生成 cache_edits 块，将最早的 N 个工具结果标记为删除。

### 缓存微压缩（Cached Microcompact）

为了避免每一轮都重复执行压缩计算，系统实现了微压缩缓存。它维护三个字段：
- messageCount：上一轮的消息数量
- messageIdentity：消息的身份指纹
- lastResult：上一次的压缩结果

当新轮次的消息数量不变且身份指纹匹配时，直接返回缓存的压缩结果，跳过压缩计算。身份指纹的计算基于第一条和最后一条消息的特征，兼顾了准确性和效率。

## 3.4 Prompt Cache 管理

### 缓存策略

Prompt Cache 是 Anthropic API 的一个重要特性，允许客户端标记哪些内容应该被服务器缓存。项目在 System Prompt 的消息块中通过 `cache_control` 字段标记缓存范围。

关键策略：
- **System Prompt 前缀缓存**：System Prompt 的前半部分（工具定义等稳定内容）被打上 `ephemeral: false` 标记，启用跨请求的持久缓存
- **对话历史缓存**：最近 N 条消息后的所有旧消息被打上 `ephemeral: true` 标记，只在本次对话中缓存
- **缓存 TTL**：Anthropic 的 Prompt Cache 有 5 分钟 TTL，在 5 分钟内的连续请求之间缓存有效

### 缓存失效

以下情况会触发缓存失效：
- System Prompt 某节内容发生变化（如 Git 分支切换）
- 对话历史新增消息
- 上下文压缩改变了消息结构
- 模型切换（不同模型的缓存键不同）

### 缓存击中率监控

系统会跟踪每次 API 响应的 `cache_read_input_tokens` 和 `cache_creation_input_tokens`，计算缓存击中率。这个数据通过 Context 分析器暴露给用户，在 UI 的状态栏中以 `缓存 85%` 的形式展示。缓存击中率低于阈值时会显示警告。

## 3.5 上下文分析器

项目实现了一个 Context 分析模块，将 Context 的使用情况可视化为用户可理解的形式。它分析以下维度：

### Token 分类
将 Context 中的 Token 按来源分类：
- 系统提示（System Prompt 各节）
- 工具定义（tool definitions）
- 对话消息（messages）
- 记忆文件（memory files）
- MCP 工具（MCP tool definitions）
- 延迟加载的工具（deferred built-in tools）

### 可视化展示
分析器将 Token 消耗以"网格方块"的形式展示。每个方块代表一定比例的 Context 使用量，不同颜色代表不同来源类别。用户可以通过这个网格直观地看到 Context 被哪些部分占用了。

### Agent 信息
显示当前对话中活跃的 Agent 列表（包括主 Agent 和子 Agent），每个 Agent 的 Token 消耗，以及 Agent 的来源（内置/插件/配置）。

### 消息级分析
对单条消息的 Token 消耗做更精细的分解：
- 工具调用 Token 数
- 工具结果 Token 数
- 附件 Token 数
- 各工具的调用/结果 Token 分布

## 3.6 消息投影（API Projection）

在将消息发送到 API 之前，系统需要进行"投影"操作。这一步将内部消息格式转换为 API 期望的格式，并应用上下文压缩。

### 投影流程

1. **克隆消息列表**：为了避免修改原始列表，先创建深拷贝
2. **检测是否需要压缩**：检查消息数量是否超过缓冲区阈值
3. **应用压缩**：如果超过阈值，对克隆的消息列表执行微压缩
4. **提交压缩结果**：将压缩后的消息列表同步回对话状态
5. **格式化输出**：根据 API 要求调整消息格式（角色交替、移除内部字段等）

### 缓冲区机制

系统使用 ConversationBuffers 管理消息的缓冲区：
- **主缓冲区**：持有所有原始消息的完整内容
- **投影缓冲区**：持有压缩后发送给 API 的消息版本
- **缓存状态**：跟踪哪些消息已经被缓存标记

当用户撤销操作或编辑消息时，系统可以回退到主缓冲区的完整内容，重新构建投影。

## 3.7 多 Agent 场景下的 Context 隔离

在多 Agent 协作场景中，Context 的隔离和共享是一个重要问题：

- **子 Agent 独立上下文**：每个子 Agent（通过 AgentTool 启动）拥有自己的消息列表，不共享主 Agent 的对话历史
- **System Prompt 前缀共享**：子 Agent 复制主 Agent 的 System Prompt 前缀（工具定义部分），以利用 Prompt Cache
- **结果回传**：子 Agent 的最终结果通过 tool_result 格式回传给主 Agent，被主 Agent 视为一次工具调用

这种隔离策略确保了子 Agent 的"噪音"不会污染主 Agent 的 Context 窗口。

## 3.8 设计权衡总结

| 权衡维度 | 选择 | 代价 |
|---------|------|------|
| 压缩粒度 | 工具结果级（微观）vs 对话轮次级（摘要） | 微观压缩更频繁但损失小；摘要压缩代价大但节省空间多 |
| 压缩时机 | 异步（不阻塞用户输入） | 压缩可能滞后于用户的新请求 |
| 缓存策略 | 激进的前缀缓存 | 缓存失效时浪费 Token |
| 压缩准确性 | 轻量级指纹（非哈希） | 存在碰撞可能，但概率极低 |
| 多 Agent 上下文 | 完全隔离 | 子 Agent 无法直接利用主 Agent 的对话历史 |
