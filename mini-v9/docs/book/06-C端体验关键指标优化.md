# 第 6 章：C 端体验关键指标优化

## 6.1 概述

C 端产品的用户体验最终体现为几个关键指标：首 Token 延迟、流式输出流畅度、工具执行可靠性、失败场景的优雅降级。这不仅是性能问题，更是产品感知质量的核心。

本章逐一剖析项目在这几个维度的设计策略。

## 6.2 首 Token 延迟（TTFT）

### 问题定义

首 Token 延迟（Time To First Token）是从用户按下回车到看到第一个输出字符的时间。对于 C 端用户，每一额外的毫秒都在消耗耐心。

### Prompt Cache 优化

首 Token 延迟的最主要来源是服务端处理 System Prompt 和对话历史的时间。项目通过 Prompt Cache 技术大幅优化这一指标：

- **System Prompt 前缀缓存**：System Prompt 的前半部分（工具定义、行为规则等稳定内容）在首次创建后即被缓存。后续请求中，API 服务器直接读取缓存，无需重新处理。
- **对话历史前缀缓存**：旧轮次的对话内容被标记为缓存。新轮次中，只有新加入的消息需要处理，历史部分直接读取缓存。
- **缓存击中率**：在理想的连续对话场景中，缓存击中率可达 70-90%，显著降低 TTFT。

### 分治策略

System Prompt 采用"分节组装"策略，只有发生变化的部分才需要重新处理。这一策略减少了 System Prompt 重建的开销：
- 稳定节（工具定义、模型行为规则）使用持久缓存
- 易变节（当前目录、Git 状态）使用临时缓存
- 更新时只重新计算发生变化的节

### 轻量级指纹

系统在消息投影阶段使用"身份指纹"来判断消息是否发生变化。这是一个基于首尾消息特征的轻量级计算，避免了完整的哈希计算开销。如果指纹匹配，直接复用上次的压缩结果。

## 6.3 流式输出流畅度

### 实时渲染

项目通过 Ink 框架的 React 渲染引擎实现终端的实时更新。流式 API 返回的每个文本增量都会触发 UI 更新：
- 文本块增量逐字符推送到消息渲染组件
- 工具调用块的 JSON 增量逐步解析并显示
- 进度事件推送到对应的工具展示组件

### 并发流式处理

在流式传输过程中，系统同时处理两件事：
1. 接收并渲染模型的输出文本
2. 接收并缓存工具调用增量

这两种流式事件通过同一个事件流到达，系统需要正确区分并分别处理。文本增量立即渲染，工具调用增量在完整后才解析执行。

### 思考过程展示

当模型使用扩展思考模式（Extended Thinking）时，思考过程会以特殊格式流式输出。系统识别思考块并单独渲染（通常以灰色或特殊样式展示），在思考完成后才展示最终输出。

### 多 Provider 的流式适配

不同 Provider 的流式传输实现各不相同：
- **OpenAI 兼容层**：将 Chat Completion 的 token-by-token delta 映射为 Anthropic 的事件格式
- **Gemini 兼容层**：将 GenerateContentResponse 流映射为对应的事件序列
- **Grok 兼容层**：类似 OpenAI 的流式映射

每种映射都由独立的适配器模块处理，上层代码无需感知差异。

## 6.4 工具执行的降级策略

### 工具不存在

当 LLM 调用了系统中不存在的工具时，StreamingToolExecutor 不会崩溃。它会立即生成一个合成错误消息：
```
<tool_use_error>Error: No such tool available: {toolName}</tool_use_error>
```
这条错误消息被包装为 tool_result，返回给 LLM。LLM 可以根据错误信息调整自己的行为（如改用其他工具）。

### 输入验证失败

每个工具都定义了 JSON Schema 输入规范。当 LLM 提供的参数不符合规范时，系统同样返回验证错误。关键设计是：
- 验证失败不阻断其他工具的执行
- 错误消息包含失败原因（如缺少必填字段、类型不匹配）
- LLM 可以据此修正参数后重新调用

### 权限拒绝

当用户拒绝工具权限时，系统返回标准化的拒绝消息：
```
User rejected tool use
```
LLM 收到拒绝后，会理解该操作未被批准，并尝试替代方案。这种设计避免了权限拒绝导致 Agent 陷入死循环。

### 工具执行超时

长时间运行的工具有隐式超时机制。对于 Bash 工具等可能长时间执行的命令：
- 中间输出通过进度事件推送到 UI
- 超时后中止执行并返回超时错误
- LLM 可以看到中间输出（如果有）并决定下一步

### 流式回退（Streaming Fallback）

当 API 流式传输过程中发生不可恢复的错误时，系统执行"流式回退"：
1. 停止当前流式传输
2. 丢弃所有已解析但未完成的工具调用
3. 重新发送简化后的请求（不含复杂工具定义）

这种策略牺牲了一些功能（工具调用），但保证了在极端场景下仍能完成对话。

## 6.5 静默失败检测与兜底

### 静默失败的定义

"静默失败"指系统在没有明显错误的情况下未能产生期望的输出。这种失败比显式错误更具伤害性，因为用户可能长时间未察觉。

### 检测机制

系统通过以下方式检测静默失败：

**无输出检测**：在 Agent 循环中记录每轮的输出状态：
- 模型调用未返回任何内容
- 模型调用了工具但工具未返回结果
- 模型陷入了重复调用同一工具的循环

**缓存异常检测**：监控缓存击中率：
- 缓存击中率异常下降（从 80% 骤降到 10%）
- 提示缓存可能被意外重建

**进度停滞检测**：跟踪长时间无进展的对话：
- 超过 N 轮对话但工具调用量很低
- 连续 N 轮调用同一工具且参数相似
- 工具调用返回结果但模型未处理

### 兜底策略

检测到静默失败后，系统执行以下策略：

**重新构建上下文**：如果怀疑上下文管理出了问题，强制刷新 System Prompt 缓存并重新发送：
- 清除系统上下文缓存
- 重新扫描 CLAUDE.md 和记忆文件
- 重新组装 System Prompt

**简化工具集**：如果怀疑工具列表影响了模型决策：
- 临时移除不相关的工具
- 减少工具定义占用的 Context 空间
- 让模型聚焦于当前任务

**主动提示**：在 UI 中显示状态信息：
- "模型响应异常，请重试或简化指令"
- "缓存命中率低，对话可能变慢"

### 用户可感知的兜底

对于最终用户，静默失败的兜底最终体现为：
- 状态栏中的缓存状态指示器
- 错误消息的清晰描述
- 明确的"重试"建议

## 6.6 Token 预算控制

### 预算上限

系统支持三层 Token 预算控制：
- **模型窗口上限**：由所选模型决定（如 200K tokens）
- **会话预算上限**：由用户或系统设置（如 100K tokens）
- **单轮预算上限**：由当前上下文状态动态决定

### 动态预算调整

预算会根据当前对话状态动态调整：
- 对话早期：分配更多 Token 给 System Prompt（完整工具定义）
- 对话中期：更多 Token 给对话历史（保持上下文连贯性）
- 对话后期：收紧预算，启动压缩

### 预算超限处理

当 Token 使用接近预算上限时：
1. 触发上下文压缩（微观压缩或摘要压缩）
2. 如果压缩后仍超限，裁剪 System Prompt 的可选节
3. 如果仍然超限，强制终止对话并提示用户

## 6.7 中断与恢复

### 用户中断

用户可以通过快捷键（ESC/Ctrl+C）中断正在执行的 Agent 循环。中断处理流程：
1. 中止当前 API 请求（通过 AbortController）
2. 丢弃所有未完成的工具调用
3. 等待正在执行的关键工具（如文件写入）完成
4. 在 UI 中显示"已中断"状态

### 会话恢复

中断后的会话可以通过两种方式恢复：
- **自动保存**：会话状态在每次轮次后自动保存到磁盘
- **手动重连**：通过 `claude attach` 命令重新连接到后台会话
- **历史查看**：通过 `claude logs` 查看历史会话记录

### 断电恢复

对于关键操作（如文件编辑），系统实现了原子化写入。即使系统在写入过程中崩溃，也不会导致文件损坏：
1. 写入临时文件
2. 确认写入完成
3. 原子重命名
4. 删除原文件（如果需要）

## 6.8 设计权衡总结

| 指标 | 优化策略 | 代价 |
|------|---------|------|
| 首 Token 延迟 | Prompt Cache + 分节组装 | 缓存维护复杂度增加，缓存失效时无帮助 |
| 流式流畅度 | React 实时渲染 + 增量更新 | 高频渲染对终端性能有要求 |
| 工具降级 | 合成错误消息返回 LLM | 消耗额外 Token 和轮次 |
| 静默失败检测 | 多重检测 + 上下文重建 | 误报可能导致不必要的操作 |
| Token 预算 | 三层预算控制 | 预算计算本身消耗计算资源 |
| 中断恢复 | AbortController + 会话持久化 | 持久化有磁盘 I/O 开销 |
