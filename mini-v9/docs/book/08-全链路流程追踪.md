# 第 8 章：全链路流程追踪

## 8.1 概述

前面七章从不同维度分析了项目的架构设计。本章将把这些维度串联起来，追踪一条用户指令从输入到输出的完整生命周期——展示各个子系统如何协调工作，以及数据流如何在它们之间流转。

我们将追踪一个典型场景：用户输入 "把这个项目的测试覆盖率报告发给我"。

## 8.2 第一阶段：用户输入与预处理

### 输入接收

1. 用户在 REPL 屏幕中输入文本，按下回车
2. REPL 组件捕获输入事件，将文本发送到 AppState
3. AppState 更新消息列表，添加新的 UserMessage
4. 触发 QueryEngine 的 submitMessage 方法

### 消息预处理

submitMessage 执行以下预处理步骤：

1. **上下文状态重置**：清除上一轮的 SystemPromptSectionState 缓存，确保系统提示使用最新内容
2. **技能发现**：如果启用了技能搜索，检查用户的输入是否匹配已安装的技能（通过语义搜索）
3. **消息投影准备**：准备发送给 API 的消息列表，包含完整对话历史和当前输入
4. **文件快照**：如果涉及文件操作，对即将编辑的文件进行快照备份

### Context 重建

在这一步，系统需要重新构建完整的 Context：

1. **System Prompt 分节组装**：调用所有注册的节计算函数，生成完整的 System Prompt
   - 日期/时间 → 当前时间
   - 工作目录 → 当前项目路径
   - Git 状态 → 当前分支和未提交变更
   - CLAUDE.md 内容 → 读取项目指令
   - 记忆文件 → 扫描 memdir 加载相关记忆
   - 工具定义 → 注册的 60+ 工具定义
   - Agent 定义 → 已加载的 Agent 信息
2. **缓存控制标记**：为不同的 System Prompt 节添加 cache_control 标记
3. **Token 预算分配**：计算当前可用的 Token 预算

## 8.3 第二阶段：API 请求发送

### 请求参数构建

将预处理后的数据组装为 API 请求参数：

1. **System Prompt**：组装完整的 System Prompt 文本块数组，已添加缓存控制
2. **消息列表**：对对话历史执行投影操作（格式转换 + 压缩）
3. **工具列表**：将所有注册工具转换为 API 工具描述格式
4. **模型参数**：设置 model、max_tokens、thinking_config 等参数
5. **扩展参数**：设置 betas（功能标记）、metadata（元数据）等

### 流式请求

1. 调用 Anthropic SDK 的流式接口
2. 创建 AbortController 用于后续中断控制
3. 启动事件流监听循环

### 错误分类与重试

如果首次请求失败：

1. 错误对象被传入 classifyAPIError 函数
2. 根据错误消息、状态码等特征分类为 7 种类型之一
3. 如果是可重试类型（rate_limit / server_error / connection_error）：
   - 计算退避延迟（指数退避 + 随机抖动）
   - 等待后重试
4. 如果超出重试次数或不可重试：
   - 报告错误给上层
   - 触发流式回退（如果是流式场景）

## 8.4 第三阶段：流式响应处理

### 事件接收

API 返回流式事件，系统处理以下关键事件：

**message_start 事件**：
- 记录消息 ID
- 初始化 Token 使用统计
- 开始计时（后续计算 TTFT）

**content_block_start 事件**：
- 如果是 text 块：初始化文本缓冲区
- 如果是 tool_use 块：解析 tool_use_id、工具名称、开始构建输入参数

**content_block_delta 事件**：
- 如果是 text_delta：追加到文本缓冲区，同时推送到 UI 渲染
- 如果是 input_json_delta：追加到工具输入参数的 JSON 缓冲区

**content_block_stop 事件**：
- 如果是 text 块：文本块完成，标记渲染完成
- 如果是 tool_use 块：解析完整的工具输入参数 JSON
- 将 tool_use 块加入 StreamingToolExecutor 的执行队列

**message_delta 事件**：
- 更新 Token 使用量和停止原因
- 推送进度到状态栏

**message_stop 事件**：
- 标记流式传输完成
- 触发后续的"后采样"处理

### 实时 UI 更新

在流式接收的同时，UI 层实时更新：

1. 文本块内容逐字符渲染到终端
2. 工具调用块以可读格式展示（工具名称 + 参数预览）
3. 状态栏更新 Token 使用量和预估成本
4. 缓存状态指示器更新

## 8.5 第四阶段：工具调度与执行

### 入队与排队

每个完整的 tool_use 块被加入 StreamingToolExecutor 的队列：

1. 解析工具定义（通过 findToolByName 查找）
2. 校验输入参数（通过 JSON Schema）
3. 创建 TrackedTool 对象（包含 ID、块、助理消息、状态）
4. 检查并发安全属性（isConcurrencySafe），决定是否可以立即执行

### 权限检查

执行前，每个工具需要经过 canUseTool 权限检查：

1. 确定当前权限模式（默认/规划/仅允许特定工具）
2. 根据模式调用对应的权限检查函数
3. 如果权限被拒绝：返回 "User rejected" 错误，LLM 自行调整
4. 如果权限批准：继续执行

### 并发执行

StreamingToolExecutor 的 processQueue 方法迭代队列，按以下规则调度：

1. 如果队列中有可执行且并发安全的工具 → 同时启动所有
2. 如果有一个非并发安全的工具 → 独占总线，阻塞后续工具
3. 工具执行过程中产生的进度事件被缓存（pendingProgress）
4. 工具执行完成后，结果被收集并包装为 tool_result

### 错误处理

工具执行中的错误按类型处理：
- **工具不存在**：立即返回合成错误消息
- **输入验证失败**：返回 Schema 校验错误
- **执行异常**：返回异常信息
- **超时中断**：返回超时错误

所有错误都被格式化为 tool_result 消息返回给 LLM，而非抛出异常。

## 8.6 第六阶段：后处理与循环判定

### 后采样钩子

流式传输完成后，进入"后采样"阶段：

1. 执行 PostSamplingHooks：
   - PromptSuggestion：分析当前对话，生成下一轮输入建议（异步 Fork）
   - ExtractMemories：分析本次对话，提取值得记忆的信息（异步 Fork）
   - SkillLearning：分析交互模式，学习用户偏好（如果启用）

### 结果收集

1. 收集所有工具执行结果
2. 将 assistant 消息（包含文本和所有 tool_use 块）添加到对话历史
3. 将所有 tool_result 消息（user 角色）添加到对话历史
4. 更新 Token 使用统计和成本追踪

### 循环判定

系统判断是否需要进入下一轮 Agent 循环：

**继续循环的条件**：
- 有工具调用且至少有一个工具返回了结果
- 未超过最大轮次限制
- 未超过 Token 预算限制
- 未收到用户中断信号

**结束循环的条件**：
- 模型返回 stop_reason = "end_turn"（认为任务完成）
- 模型返回纯文本且无工具调用（正常单轮回答）
- 超过最大轮次限制
- 超过 Token 预算限制
- 用户主动中断

### 上下文压缩

如果判定需要继续循环且消息数量超过阈值：

1. 执行微观压缩（microcompact）：删除最旧的工具执行结果，保留最近的
2. 如果压缩幅度不足，触发摘要压缩（通过 Fork 子 Agent）
3. 更新 CachedMCState，记录本次压缩的结果
4. 在 UI 中显示压缩边界提示

### 预算检查

每轮结束后检查预算使用：
1. 计算已用 Token 与总预算的比例
2. 如果接近预算上限 → 通知下一轮使用更激进的压缩
3. 如果已超预算 → 终止循环，提示用户

## 8.7 完整数据流图

```
用户输入 "测试覆盖率报告"
    │
    ▼
REPL 组件 → AppState 更新 → QueryEngine.submitMessage
    │
    ▼
Context 构建
    ├── System Prompt 分节组装 (日期/Git/CLAUDE.md/记忆/工具/Agent)
    ├── 消息投影 (格式转换 + 压缩 + 缓存标记)
    └── Token 预算计算
    │
    ▼
API 请求 (带有 200K tokens 的上下文)
    │
    ▼
流式响应
    ├── "我来帮你运行测试覆盖率的命令..."
    ├── tool_use: BashTool → npm run test:coverage
    └── tool_use: GlobTool → find coverage report files
    │
    ▼
StreamingToolExecutor 并发执行
    ├── BashTool → npm run test:coverage (并发安全)
    └── GlobTool → 查找 coverage/lcov-report/index.html
    │
    ▼
结果收集
    ├── BashTool 结果: 覆盖率数据输出
    └── GlobTool 结果: 报告文件路径
    │
    ▼
下一轮 API 请求 (带工具结果)
    │
    ▼
模型分析结果并生成最终回复
    └── "测试覆盖率是 85%，报告地址是..."
    │
    ▼
Post-Sampling Hooks
    ├── 记忆提取 (可选)
    ├── Prompt 建议 (后台 Fork)
    └── 上下文压缩评估
    │
    ▼
UI 渲染最终回复 → 用户看到结果
```

## 8.8 各子系统的参与时机

| 阶段 | 参与子系统 | 关键类/模块 |
|------|-----------|------------|
| 输入处理 | UI + State + QueryEngine | REPL, AppState, QueryEngine |
| Context 构建 | Context + Memdir + ClaudeMd | SystemPromptSection, memdir, claudeMd |
| API 通信 | API Layer + Retry | claude.ts, withRetry, classifyAPIError |
| 流式处理 | Query + Stream | Stream, Query |
| 工具调度 | Tool System | StreamingToolExecutor, tools.ts |
| 权限检查 | Permission System | canUseTool, PermissionMode |
| 结果收集 | QueryEngine | submitMessage yield |
| 后处理 | Hooks + Memory + Suggestion | PostSamplingHooks, extractMemories, promptSuggestion |
| 上下文压缩 | Compact | microcompactToolResults, cachedMicrocompact |
| 预算控制 | CostTracker | cost-tracker.ts |
| 中断恢复 | AbortController + Session | sessionRestore |

## 8.9 总结

通过全链路追踪，我们可以看到项目的几个核心设计原则：

**分层解耦**：每一阶段有清晰的职责边界，阶段之间通过消息传递（而非共享状态）通信。

**弹性恢复**：在任何阶段的失败场景中，系统都有对应的降级和恢复策略——从 API 重试到工具降级到上下文重建。

**异步后台处理**：非关键路径的操作（记忆提取、Prompt 建议、上下文压缩）都通过后台 Fork 执行，不阻塞主流程。

**用户感知优先**：流式渲染、实时进度更新、缓存状态提示——所有设计都以用户的实际感知体验为准。

这八大章节构成了对 mini-v9 项目完整的技术架构解析。每一章都可以独立阅读，但合在一起才能看到整个系统如何运作的完整图景。
