  实施计划

  Phase 1 — 高影响，低/中工作量 (先做)

  1.1 每轮都跑 snip projection + microcompact

  mini-v9/src/query.ts 的 while 循环中，在 projectMessagesForAPI 之后、API 调用之前，插入：
  // Run snip compact every turn (not just on /force-snip)
  const snipResult = snipCompactIfNeeded(toSnipEntries(conversation))
  if (snipResult.executed) applySnipToBuffers(conversation, snipResult.entries)

  // Run microcompact every turn (not just during reactiveCompact)
  const microcompacted = microcompactToolResults(messagesForAPI)

  文件改动: query.ts（约 15 行插入）
  收益: 减少上下文膨胀，降低 prompt-too-long 触发概率

  1.2 预测性 autocompact

  API 调用前估算当前 token 是否接近上下文窗口上限，如果是则提前触发 compactMessages()：
  const estimatedGrowth = estimateMaxTurnGrowth(model)
  const threshold = getEffectiveContextWindowSize(model) - estimatedGrowth
  if (currentTokens > threshold) { /* trigger compact proactively */ }

  文件改动: query.ts + 新增 autoCompact.ts helper（estimateMaxTurnGrowth、getEffectiveContextWindowSize）
  收益: 避免 API 返回 413 后再 recovery，减少 token 浪费

  1.3 模型 fallback

  retryWithBackoff 重试用完后，如果错误是 503/overloaded 且有后备模型，自动切换到后备模型重试：
  if (category === 'server_error' && fallbackModel) {
    currentModel = fallbackModel
    // Strip signatures, clear partial state, retry
  }

  文件改动: query.ts（~40 行），entrypoints/cli.ts（传递 fallback model 参数）
  收益: 提高服务可用性，减少用户手动切换模型

  Phase 2 — 中影响，高工作量 (次要做)

  2.1 Context collapse

  实现阶段式上下文折叠：将早期对话折叠为摘要，保留尾部详细上下文。关键接口：
  - applyCollapsesIfNeeded(messages) — 将可折叠的旧消息替换为摘要
  - recoverFromOverflow(messages) — 收到 413 时 drain staged collapses
  - isWithheldPromptTooLong(msg) — 判断是否 withhold 413 错误

  文件改动: 新增 services/contextCollapse/index.ts + operations.ts + persist.ts（参考 src/ 但可简化）
  收益: 比 reactive compact 更精细的压缩，保留更多有用上下文

  2.2 LLM 摘要压缩

  将 compactMessages() 从 deterministic 裁剪升级为 LLM 调用生成摘要。需要：
  - deps.autocompact(messages, toolUseContext, ...) — 调用 LLM 生成摘要
  - buildPostCompactMessages(result) — 构建压缩后的消息数组
  - Yielding compact summary messages for UI display

  文件改动: 新增 services/compact/llmCompact.ts，修改 query.ts 和 autoCompact.ts
  收益: 更高质量的压缩，保留语义信息而非简单裁剪

  Phase 3 — 低影响，按需做

  3.1 Token budget: 在 query.ts 中增加 TOKEN_BUDGET feature gate，实现 checkTokenBudget()、createBudgetTracker()。每轮结束后检查输出 token 是否超出 budget，超出时插入 nudge
  message 自动续费。

  3.2 流式工具执行: 参考 src/ 的 StreamingToolExecutor，将工具执行和模型流式输出并行化。重大重构，建议在 Phase 2 之后。

  3.3 图片/媒体错误: 捕获 ImageSizeError / ImageResizeError，生成用户友好的错误消息。

  3.4 缓存警告: 在 assistant message 结束后检查 usage.cache_read_input_tokens 占比，低于阈值时 yield cache warning。

  推荐执行顺序

  Phase 1 (立即做):
    1.1 Snip + microcompact every turn  →  1 天
    1.2 Predictive autocompact          →  1 天
    1.3 Model fallback                  →  0.5 天

  Phase 2 (后续):
    2.1 Context collapse                →  2-3 天
    2.2 LLM auto-compact                →  2-3 天

  Phase 3 (按需):
    Token budget / 流式执行 / 媒体恢复  →  按需排期

  收益与风险评估

  - Phase 1 的 3 项改动风险极低（均为现有能力的增强而非重构），收益显著（减少 413 概率、提高可用性）
  - Phase 2 的 context collapse 需要新增模块，但 src/ 的存根已提供参考接口；LLM autocompact 需要额外的 API 调用，注意 cost
  - Phase 3 的流式工具执行是最大重构，建议先确认确有需求再投入
